# ADR-0012: 食堂用量怎么补：按每份记，规则值写明出处

- Status: Proposed（2026-10-19）
- Deciders: @TERRYYYC（[#169](https://github.com/TERRYYYC/canteen-os/issues/169)、[#170](https://github.com/TERRYYYC/canteen-os/issues/170)）

## Context

收藏解析出的菜谱要用在本周采购和今日备料上。2026-10-19 只读盘点了本机已解析的 49 道菜，只记数量：

| 项 | 数量 |
|---|---|
| 食材行 | 867 |
| 用量有明确重量或体积 | 155（18%） |
| 只有「点、少许、一点点」这类原话 | 241（28%） |
| 完全没说用量 | 374（43%） |
| 个数、勺碗把、比例，或几种说法混在一起 | 97（11%） |
| 主料行（按名字粗分） | 175，其中 108 行（62%）没说用量，27 行有重量 |
| 调料行（按名字粗分） | 692，其中 486 行只有原话或没说 |
| 主料全部有重量的菜 | 7 道 |
| 有能用份数的菜 | 0 道：46 道没说，3 道说的是「两三个人吃」这类话 |
| 带「没说清」的步骤 | 403 步里有 380 步，共 391 条 |

缺口主要出在视频本身：不少视频几乎没有口播，有口播的也常说「来点」。抽查 3 道菜，解析没有漏项，也没有拿瓶身净含量或电饭煲刻度去推算用量，所以重跑解析补不回来。另外，视频本来就是家庭量，就算说全了，也要师傅换成食堂量（[roadmap-v2](../roadmap-v2.md) 第 60 行）。

这些缺口对采购和备料的影响（代码位置以 main `e8febfe` 为准）：

- **采购：** 按「用量 × 计划份数 ÷ 配方份数」计算（`packages/core/src/team-meals.ts:81-86`）。缺配方份数时，每一行都显示「配方基准份数未录」，归入「数量待定」（`team-meals.ts:241-257`；文案见 `packages/web/src/pages/purchase-list.ts:41-48`）。
- **固定菜谱：** 只有克、斤、公斤、毫升、升、个、只、片能变成可计算的数（`packages/worker/src/knowledge-materialization.ts:73-97`）。勺、碗、把和「点」只保留原话。
- **备料：** 没有份数就不能按当天份数放大，页面只显示标着「原方」的家庭量。没写切法的显示「还没写怎么切 · 问师傅」，没写时机的归入「时机未录」（`packages/web/src/pages/prep-list.ts:156-158`、`:199`、`:211-220`）。

四条线设计稿的方向是：采购按「每份用量 × 份数」算，「用量按『我们的做法』算」（[product-structure](../design/four-lines/product-structure.md) 第 91、103 行）。菜库会慢慢变成「我们厨房的菜谱」（同文件第 30 行）。

现有规矩只说了不能怎样：

- 未知保持未知，不补 1、0、50，也不编「适量」（[当前工作合同](../current-contract.md) 第 49 行、`CONTRIBUTING.md:104`、[team-meals 合同](../specs/team-meals-contract.md) INV-1）。
- AI 得出的份数不能直接当配方份数（`skills/video-recipe-ingest/references/candidate-contract.md:9`）。
- AI 不署名审批（`skills/video-recipe-ingest/SKILL.md:32`）。
- 复核在 app 外（[ADR-0011](0011-recipe-review-outside-app.md)）。

但有几件事还没定：谁来补用量、按什么基准补、补出来的数怎么标出处、AI 能做到哪一步。

盘点时列出的可选方案：

1. **师傅逐道补。** 最准，但一道约 30 分钟，49 道约 25 小时。
2. **师傅先定「每份用量」的规则，每道菜只补例外。** 快，但按类给的值会有偏差，要能分清哪些是规则值、哪些是实称值。
3. **AI 按同类菜给参考值，标成「参考」。** 最快，但进了 app 之后，采购员和帮厨分不清参考值和真值，等于让 AI 冒充师傅。
4. **只补采购和备料必需的最少字段。** 这一条划的是范围，要和 1 或 2 搭配。

还有一个附带选项：调料改成「常备调料，看库存补」，不按菜计算。

Terry 2026-10-19 的决定（[#170 评论](https://github.com/TERRYYYC/canteen-os/issues/170)原文）：

> 1. 补全方向：**最少字段 + 规则打底**——只补采购和备料必需的字段；份数一律按「每份」记，由师傅先定每份用量的规则；测试周和常做的菜由师傅逐道实补；AI 参考值只印在补料表上，不进数据。
> 2. 按师傅规则填的值：**能进数据，写明出处**（谁、哪天定的规则）。
> 3. 先补：**主料已有重量的 7 道**。
> 4. 调料：**仍按菜算**，不改成「常备调料」。

## Decision

### 1. 原方和「我们的做法」分开记

- **原方**：视频或其他来源里的原话，照旧记在 `originalAmount`、`originalPreparation`。不改，不换算，不参与计算。
- **我们的做法**：食堂实际用的量，记在结构化用量 `qty`（`Quantity`）。采购和备料只按它算。
- 还没有「我们的做法」的地方写未知。不拿原方的家庭量去放大，也不让 AI 从原方推算。

### 2. 份数一律按「每份」记

- 按本 ADR 补的菜，配方份数 `baseServings` 写 1，每行用量都是一份的量，例如「鸡腿肉每份 150 g」。采购照旧按 `qty × 计划份数 ÷ 1` 计算，采购引擎不用改。
- 已有按其他份数记的菜（例如演示菜的 `baseServings` 是 50）继续有效，不迁移。
- 份数不从视频推算。视频里说的「两三个人吃」只作为原方参考保留。
- `schemas/dish.schema.json:21` 对 `baseServings` 的说明目前是「食堂尺度（如 50）」，实施时改成「推荐按每份记 1」。

### 3. 一行用量只有三种出处，看得出是哪一种

| 出处 | 是什么 | 进不进计算 |
|---|---|---|
| 师傅实称 | 师傅对这道菜实际称过，或直接给出的每份用量 | 进 |
| 师傅规则 | 按师傅定的规则填的每份用量 | 进，并引用所用的规则 |
| 原方 | 视频或来源里的原话 | 不进，只作为 `originalAmount` 显示 |

**关于规则：**

- 规则由师傅定，例如「荤菜每份主料净重 X 克」「盐每份 X 克」。
- 每条规则要记下：规则 id、内容、适用范围、谁定的、哪天定的（Terry 决定 2）。规则写进仓库，作为公开资料的一部分；具体放在哪，见文末「签收时要定的」第 1 条。
- 每个按规则填的用量都要引用规则 id。
- 师傅改了规则，已经固定的版本不变。要用新规则，就补成新版本，排菜时换用新版本（[ADR-0009](0009-sqlite-knowledge-base.md) 第 6 条、ADR-0011 第 3 条）。

**关于实称值：** 在 PR 说明或知识库修订说明里写明是谁、哪天给的（和 [#156](https://github.com/TERRYYYC/canteen-os/issues/156) 的做法一样）。同一行既有规则值又有实称值时，以实称值为准。

**关于字段：**

- 现有 schema 里没有地方标用量出处。`components[].confidence` 记的是机器解析的置信度（`schemas/dish.schema.json:58`、`schemas/common.schema.json:68`，`source` 只能取 `manual`、`video`、`llm-inference`），含义不同，不复用。
- 实施时新加一个可选字段，见下文「签收后的实施」里的 schema 一行。

**关于显示：** 帮厨和采购员看到的页面不区分规则值和实称值，都按「用量」显示。出处在数据和菜品库里可以查到。理由同 ADR-0011：他们看不懂的、开发用的东西不放在眼前。

### 4. 规则只能由师傅定，AI 不定规则、不代填

师傅没定规则、也没给实称值的行，继续写未知。AI 不署名，也不出现在任何出处里（`skills/video-recipe-ingest/SKILL.md:24`、`:32`）。

### 5. AI 参考值只印在补料表上

- 补料表上可以有一栏「同类菜常见范围（仅供参考）」。这一栏默认不印，需要时才加，加的时候要在表上写明数是从哪来的。
- 这一栏不进 `data/`，不进 app，也不进知识库。
- 数据里只有师傅写下的数。

### 6. 调料仍按菜算（Terry 决定 4）

调料和主料一样，走第 3 条说的三种出处：

- **优先用规则。** 请师傅给常用调料定「每份大约多少」，例如盐、味精、鸡精、糖、生抽、老抽、蚝油、料酒、食用油。需要的话，可以按做法再细分，炒菜、炖菜、凉菜各定一个数。49 道菜里出现在 2 道以上的食材名共 111 个，常用调料集中在其中十几种，定一次就能覆盖大部分调料行。
- **规则不合适的菜**，由师傅逐道给实称值。
- **「点、少许、一点点、来点」**：
  - 原话照旧留在 `originalAmount`。
  - 只有被规则覆盖，或者师傅给了实称值，这一行才有数。两样都没有的，继续写未知，采购页照旧显示「原用量未录」。
  - 不把「点」换成 0、1 或「适量」。只有来源原话就是「适量」时，才记为 `to-taste`（[team-meals 合同](../specs/team-meals-contract.md)第 61 行）。
- **炸油、过油用油**：记每份实际耗掉多少油，不记锅里放了多少。「油宽点」「炸鸡用油」说的是锅里的油量，不是要买的量。
- **水**：不是采购项。要不要放进标准食材目录，由 [#167](https://github.com/TERRYYYC/canteen-os/issues/167) 定。
- **对采购页的影响**：采购页对每种料分别判断能不能算（`team-meals.ts:241-257`）。调料还没补齐时，只有这几行显示「数量待定」，主料照常计算。整张清单的合计仍按 INV-8 标为不完整，不当成总量。

### 7. 这一轮只补最少的字段

- **采购需要：**
  - 份数（写 1）。
  - 每行每份的用量：g 或 ml；按个计的，写个数，再在标准食材上记每个多少克。
  - 毛重还是净重。
  - 绑定的标准食材。标准食材的目录、净料率、采购规格（供应商、包装、价格）以及怎么绑定，按 #167（D2）的结论办。
- **备料需要（主料）：**
  - 切法：从 `data/techniques.json` 里已有的技法选，记在 `prep.techniqueRef`。
  - 大小：记在 `prep.size`。
  - 准备时机：记在 `prep.timing`。
  - 要提前多久：腌、泡、卤、醒这类步骤要写。
  - 视频里「没说清」的地方怎么带到备料页，按 [#168](https://github.com/TERRYYYC/canteen-os/issues/168)（D3）的结论办。
- **这一轮不补：** 火候、时长、出锅标准，留给菜品库以后补。

### 8. 先补什么

- **第一批**：主料已有重量的 7 道（Terry 决定 3）。主料由师傅逐道实补，调料先用规则（#172）；这 7 道用到的标准食材和采购规格见 #173。
- **测试周要用的菜和常做的菜**：由师傅逐道实补。
- **其他菜**：先用规则打底，师傅过一遍，改掉不合适的。

### 9. 和 ADR-0011、「未知写未知」的关系

- **复核仍在 app 外**，ADR-0011 不变。补料也在 app 外进行：师傅在补料表上填，或者口述，再由 Claude 整理。
- **补好的用量写到哪：**
  - Terry 10/19 说先不写知识库，所以首批走数据 PR，写进 `data/dishes/`，接 #156。
  - 以后能写知识库了，就写成知识库菜谱的新版本，排菜时换用新版本。
  - 合并数据 PR 不等于厨房核定（`CONTRIBUTING.md:102`）。
- **规则值不算「补数」。** 它是师傅的决定，数据里写明了出处。没有师傅的决定，就仍然是未知。当前工作合同第 49 行、`CONTRIBUTING.md:104`，以及 team-meals 合同的 INV-1、INV-7、INV-8 都不变。
- **公开范围。** `data/` 是公开资料（GitHub Pages）。规则和用量是厨房的做法，可以公开；视频链接、原片截图、原话以外的来源原文不进 `data/`（[ADR-0010](0010-knowledge-source-access.md)）。

**不在本 ADR 范围内的事：**

- 师傅能抽多少时间，用纸、表格还是口述。
- 标准食材的采购规格由谁填、在哪填。
- 菜谱食材绑定标准食材在哪做。

这三件按 #170 的安排，等 #167 的提案给出选项后再定。

## Consequences

**好处：**

- 一套规则能让很多菜同时有数。
- 份数问题用一条规则就解决了。
- 只要 #167 把采购规格补上，采购员就能看到主料要买多少。

**代价：**

- 规则值是估算，单道菜会有偏差。以后可以靠「做完以后」的反馈（product-structure 第 102 行），把规则值换成实称值，这不在本轮。
- 调料仍按菜算，486 行调料是补料工作里量最大的一块。规则没覆盖到的调料，采购页上会继续出现「原用量未录」。
- 要新加 schema 字段（用量出处）和规则文件，并按 schema → types → data → docs 的顺序同步。都是可选字段，不是破坏性变更。

**不受影响的：**

- 采购引擎的计算公式。
- 已经固定的菜单版本。
- 采购员自己的判断（待核对 / 待买 / 已有 / 已买）。

**签收后要同步的文档：**

- 当前工作合同第 49 行后面加一句，引用本 ADR。
- `CONTRIBUTING.md:104` 加上引用。
- `schemas/dish.schema.json:21` 改 `baseServings` 的说明。
- 等 #165 合并后，在 `docs/video-import.md` 里写明补料表的用法。

## 签收时要定的

1. **规则放在哪：** `data/` 里的受控文件，还是 docs 里的一张表。推荐放 `data/`：每个规则值都能引用规则 id，也能做校验。
2. **「谁定的」写什么：** `data/` 是公开的，公开写名字，还是只写「师傅」。
3. **规则分多细：** 只按食材分（例如「盐每份 X 克」），还是按食材再加做法（炒、炖、凉拌）分。推荐先只按食材分，个别不合适的菜逐道改。
4. **页面显示：** 帮厨和采购页不区分规则值和实称值，可以吗？推荐不区分。
