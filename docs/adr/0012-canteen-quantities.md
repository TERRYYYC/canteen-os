# ADR-0012: 食堂用量怎么补，视频里没说清的地方怎么带到备料页

- Status: Proposed（2026-10-19）
- Deciders: @TERRYYYC（[#169](https://github.com/TERRYYYC/canteen-os/issues/169)、[#170](https://github.com/TERRYYYC/canteen-os/issues/170)）

## Context

收藏解析出的菜谱要用在本周采购和今日备料上。2026-10-19 只读盘点了本机已解析的 49 道菜，只记数量：

| 项 | 数量 |
|---|---|
| 食材行 | 867 |
| 用量有明确重量或体积 | 155（18%） |
| 只有「点、少许、一点点」这类原话 | 241（28%） |
| 完全没说用量 | 374（43%） |
| 个数、勺碗把、比例，或几种说法混在一起 | 97（11%） |
| 主料行（按名字粗分） | 175，其中 108 行（62%）没说用量，27 行有重量 |
| 调料行（按名字粗分） | 692，其中 486 行只有原话或没说 |
| 主料全部有重量的菜 | 7 道 |
| 有能用份数的菜 | 0 道：46 道没说，3 道说的是「两三个人吃」这类话 |
| 带「没说清」的步骤 | 403 步里有 380 步，共 391 条 |

缺口出在哪，只核了一部分：

- 抽查的 3 道菜，解析没有漏项，也没有拿瓶身净含量或电饭煲刻度去推算用量。这 3 道的缺口出在视频本身，重跑解析补不回来。
- 另有 4 条视频几乎没有口播（转写不到 60 字）。
- 其余 46 道没有逐条对照原片。它们的缺口里，可能有原片说了却没提取出来的，也可能有原话里有数、却没写成结构化数值的。这两种要修解析，不该让师傅补。补料表会把每个缺口分开记（见「签收后的实施」里 #171 那一行）。

另外，视频本来就是家庭量，就算说全了，也要师傅换成食堂量（[roadmap-v2](../roadmap-v2.md) 第 60 行）。

这些缺口对采购和备料的影响（代码位置以 main `e8febfe` 为准）：

- **采购：** 按「用量 × 计划份数 ÷ 配方份数」计算（`packages/core/src/team-meals.ts:81-86`）。缺配方份数时，每一行都显示「配方基准份数未录」，归入「数量待定」（`team-meals.ts:241-257`；文案见 `packages/web/src/pages/purchase-list.ts:41-48`）。
- **固定菜谱：** 知识库里标成精确数（`kind=exact`）、单位是克、斤、公斤、毫升、升、个、只、片的用量，会直接写成可计算的 `qty`（`packages/worker/src/knowledge-materialization.ts:73-97`，写入在 `:88-92`）。勺、碗、把和「点」只保留原话。也就是说，原方里没有歧义的家庭量，现在也会进计算。候选合同允许把这类原话转成数值（`skills/video-recipe-ingest/references/candidate-contract.md:11`），#159 新加的解析规则还会让这类数更多。
- **备料：** 没有份数就不能按当天份数放大，页面只显示标着「原方」的家庭量。没写切法的显示「还没写怎么切 · 问师傅」，没写时机的归入「时机未录」（`packages/web/src/pages/prep-list.ts:156-158`、`:199`、`:211-220`）。

四条线设计稿的方向是：采购按「每份用量 × 份数」算，「用量按『我们的做法』算」（[product-structure](../design/four-lines/product-structure.md) 第 91、103 行）。菜库会慢慢变成「我们厨房的菜谱」（同文件第 30 行）。

现有规矩只说了不能怎样：

- 未知保持未知，不补 1、0、50，也不编「适量」（[当前工作合同](../current-contract.md) 第 49 行、`CONTRIBUTING.md:104`、[team-meals 合同](../specs/team-meals-contract.md) INV-1）。
- AI 得出的份数不能直接当配方份数（`skills/video-recipe-ingest/references/candidate-contract.md:9`）。
- AI 不署名审批（`skills/video-recipe-ingest/SKILL.md:32`）。
- 复核在 app 外（[ADR-0011](0011-recipe-review-outside-app.md)）。

但有几件事还没定：谁来补用量、按什么基准补、补出来的数怎么标出处、AI 能做到哪一步。

盘点时列出的可选方案：

1. **师傅逐道补。** 最准，但一道约 30 分钟，49 道约 25 小时。
2. **师傅先定「每份用量」的规则，每道菜只补例外。** 快，但按类给的值会有偏差，要能分清哪些是规则值、哪些是实称值。
3. **AI 按同类菜给参考值，标成「参考」。** 最快，但进了 app 之后，采购员和帮厨分不清参考值和真值，等于让 AI 冒充师傅。
4. **只补采购和备料必需的最少字段。** 这一条划的是范围，要和 1 或 2 搭配。

还有一个附带选项：调料改成「常备调料，看库存补」，不按菜计算。

Terry 2026-10-19 的决定（[#170 评论](https://github.com/TERRYYYC/canteen-os/issues/170)原文）：

> 1. 补全方向：**最少字段 + 规则打底**——只补采购和备料必需的字段；份数一律按「每份」记，由师傅先定每份用量的规则；测试周和常做的菜由师傅逐道实补；AI 参考值只印在补料表上，不进数据。
> 2. 按师傅规则填的值：**能进数据，写明出处**（谁、哪天定的规则）。
> 3. 先补：**主料已有重量的 7 道**。
> 4. 调料：**仍按菜算**，不改成「常备调料」。

Terry 同一天的补充决定（[#170 评论](https://github.com/TERRYYYC/canteen-os/issues/170#issuecomment-6257683642)原文）：

> 1. **首批 7 道走知识库，不走 Git 数据。** 这条路要写知识库：先把 7 道同步到远端（#159），再新建标准食材（#173），最后补成新版本、排菜时固定（#172）。这些写入都在第 2 波、对应设计签收以后由子线程做，现在不写。
> 2. **本版只开 ADR-0012 一篇。** #177 的 schema 决定并进 ADR-0012，不另开 0013；#178 的「采购规格单独固定」留到下一版。

所以本 ADR 也收下 #168（D3）的设计结论：固定菜谱时，带上视频里没说清的地方（第 11 条）。设计细节在 [docs/design/recipe-unknowns/README.md](https://github.com/TERRYYYC/canteen-os/blob/14fecd14a94317bebfece39c5da3e6a205498caa/docs/design/recipe-unknowns/README.md)（PR [#177](https://github.com/TERRYYYC/canteen-os/pull/177)，HEAD `14fecd1`），下文简称「D3 设计」。

## Decision

### 1. 原方和「我们的做法」分开记，原方的数不进计算

- **原方**：视频或其他来源里的原话，照旧记在 `originalAmount`、`originalPreparation`。
  - 原方里的数，哪怕没有歧义（比如「鸡腿 500 g」），也只进 `originalAmount`，不进 `qty`。
  - 补料表或菜品库如果要用结构化的原方数，另设一个原方结构化字段。这个字段只用来显示，不参与计算。
- **我们的做法**：食堂实际用的量，记在结构化用量 `qty`（`Quantity`）。采购和备料只按它算。
  - `qty` 只能来自有出处的行，出处见第 3 条：师傅实称、师傅指定或师傅规则。
  - 份数写 1 的菜，每一行有数的 `qty` 都必须带出处。缺出处的，数据校验拒绝。
  - 份数不是 1 的旧数据不受这条校验约束，比如演示菜，它的用量是人工录入的。
- 还没有「我们的做法」的地方写未知。不拿原方的家庭量去放大，也不让 AI 从原方推算。
- **为什么必须这样：** 原方「鸡腿 500 g」是两三个人的量。如果它照现在的做法成了 `qty`，又按第 2 条把份数写成 1，计划 100 份时采购会算出 50 kg。
- **和 ADR-0011 的关系：** ADR-0011 的「后果」第 2 条写的是现状：AI 解析的用量会直接进入备料和采购估算。本 ADR 签收并实施后改为：原方的数只显示，不进计算。ADR-0011 的「决定」部分不变。

**知识库和 Worker 两边怎么处理原方的数。** 首批 7 道走知识库，固定时要经过 Worker，所以这条路上一定会碰到原方的数。

知识库这边（私有仓库，要配合，见「签收后的实施」里知识库那一行）：

- 菜谱修订里，每一行的原方用量和食堂用量分开存。现在一行只有一个 `amount`（`packages/web/src/api/knowledge-types.ts:3-4`）。
  - **原方**：原话，加上可选的结构化原方数。导入器从原话里解析出的数（例如「5斤」「600克」）只写到这里。
  - **食堂用量**：数值、单位和出处（实称、指定，或规则加规则 id；谁、哪天）。只在补料时由人写入。
- 已有的修订不就地改（ADR-0009）。7 道同步到远端以后，补好的用量存成新版本。

Worker 这边（`packages/worker/src/knowledge-materialization.ts`）：

- **新格式的修订**（原方和食堂用量分开存的）：食堂用量写成 `qty`，带上出处；原方只写进 `originalAmount` 和原方结构化字段，不写 `qty`。
- **旧格式的修订**（一行只有一个 `amount` 的）：照现在的做法生成。原因是，已经固定过的版本再固定一次，生成的文件必须和上次逐字节相同，否则写入会被拒绝（`packages/worker/src/write.ts:116`）。
- **旧格式修订里份数写了 1 的**：固定时，按上面「份数写 1 的菜每个 `qty` 都要有出处」的校验拒绝，因为它的 `qty` 来自原方，没有出处。页面上用人话说明，例如「份数按每份记的菜，每个用量都要写明出处」。这样「500 g 被当成每份用量」的错就发布不出去。

### 2. 份数一律按「每份」记

- 按本 ADR 补的菜，配方份数 `baseServings` 写 1，每行用量都是一份的量，例如「鸡腿肉每份 150 g」。采购照旧按「`qty` × 计划份数 ÷ 1」计算，采购引擎不用改。
- 已有按其他份数记的菜，比如演示菜的 `baseServings` 是 50，继续有效，不迁移。
- 份数不从视频推算。视频里说的「两三个人吃」只作为原方参考保留。
- `schemas/dish.schema.json:21` 对 `baseServings` 的说明，目前是「食堂尺度（如 50）」，实施时改成推荐按每份记 1。

### 3. 有数的值只有三种出处，每个值都看得出是哪一种

| 出处 | 是什么 | 进不进计算 |
|---|---|---|
| 师傅实称 | 这道菜按食堂做法**实际称过**的量 | 进 |
| 师傅指定 | 师傅对这道菜直接给的数，没有称过 | 进 |
| 师傅规则 | 按师傅定的规则填的数，引用所用的规则 | 进 |
| 原方 | 视频或来源里的原话或数 | 不进，只用来显示 |

**适用范围**：这条管菜里每一行的 `qty`，也管所绑标准食材里，按规则或由师傅给出的厨房换算值，也就是**净料率**和**每个多少克**（`pcsToGram`）。后两项是 #167 的提案（[#178](https://github.com/TERRYYYC/canteen-os/pull/178) §3.1、§4.4）交给本 ADR 定出处的。

**几个值都有时**：同一行或同一个值既有实称、又有指定或规则时，按「实称 → 指定 → 规则」的顺序，用排在前面的那个。

**规则：**

- 规则由师傅定，例如「荤菜每份主料净料 X 克」「盐每份 X 克」「生抽每份 X 毫升」「去骨鸡腿净料率 X」。
- 每条规则要记下：规则 id、内容、适用范围、单位、谁定的、哪天定的（Terry 决定 2）。规则写进仓库，作为公开资料的一部分；具体放在哪，见文末「签收时要定的」第 1 条。
- 每个按规则填的值都要引用规则 id。
- 师傅改了规则，已经固定的版本不变。要用新规则，就补成新版本，排菜时换用新版本（[ADR-0009](0009-sqlite-knowledge-base.md) 第 6 条、ADR-0011 第 3 条）。

**实称和指定：** 要记下是谁、哪天给的。PR 说明或知识库修订说明里也要写（和 [#156](https://github.com/TERRYYYC/canteen-os/issues/156) 的做法一样）。没称过的数不能记成实称。

**字段：**

- 现有 schema 里没有地方标出处。`components[].confidence` 记的是机器解析的置信度（`schemas/dish.schema.json:58`、`schemas/common.schema.json:68`，`source` 只能取 `manual`、`video`、`llm-inference`），含义不同，不复用。
- 新字段见下文「签收后的实施」里 schema 那一行。

**显示：** 帮厨和采购员看到的页面，不区分实称、指定和规则，一律按「用量」显示。出处在数据和菜品库里可以查到。理由同 ADR-0011：他们看不懂的、开发用的东西不放在眼前。

### 4. 单位和毛重、净重的口径

**单位跟所绑标准食材的基准单位走。**

- 基准单位是 g 的，规则值和实称值都写 g；是 ml 的写 ml；是 pcs 的写个数。
- 采购引擎不做体积和重量的互换（`packages/core/src/procurement/engine.ts:161-164`）。比如生抽按 ml 买，规则写成克就算不出来。
- 这样就暂时不用加密度，也不用加「每勺多少克」（[#178](https://github.com/TERRYYYC/canteen-os/pull/178) §3.2）。

**`qty` 一律记净料。** 净料指去皮、去骨、择洗之后下锅的量。

- 净料换成毛料只在采购引擎里做一次：毛料 = 净料 ÷ 净料率 × 备量系数（`engine.ts:222`、`:342-346`）。
- 师傅给的如果是毛料，整理成数据时，先用同一个标准食材的净料率换成净料再存。
- 净料率不知道的，这一行不写 `qty`，等师傅一起给出净料率。

**算例**（只用来验收接口，不是配方建议；备量系数取 1）：

| 情况 | 存成 | 采购算出 |
|---|---|---|
| 师傅给净料 100 g/份，净料率 0.8，计划 100 份 | `qty` = 100 g | 100 × 100 ÷ 0.8 = 12 500 g = 12.5 kg 毛料 |
| 师傅给毛料 125 g/份，其余同上 | 先换成净料 125 × 0.8 = 100 g，`qty` = 100 g | 同样是 12.5 kg |
| 错误做法：把毛料 125 g 直接当净料存 | `qty` = 125 g | 125 × 100 ÷ 0.8 = 15 625 g = 15.625 kg，多买 25% |

**按个计的料**（例如鸡蛋）：

- `qty`、基准单位、包装单位都是 pcs 时，直接按个算。不套净料率（`engine.ts:223`），也不需要每个多少克。
- 只有个数和重量之间要换算时，`pcsToGram` 才是必填（`engine.ts:163`、`:182`）。比如菜里写克，但按个买。
- 最少字段里不要求师傅为按个买的料额外去称重。

### 5. 规则只能由师傅定，AI 不定规则、不代填

师傅没定规则、没给指定值、也没实称过的行，继续写未知。AI 不署名，也不出现在任何出处里（`skills/video-recipe-ingest/SKILL.md:24`、`:32`）。

### 6. AI 参考值只印在补料表上

- 补料表上可以有一栏「同类菜常见范围（仅供参考）」。这一栏默认不印，需要时才加，加的时候要在表上写明数是从哪来的。
- 这一栏不进 `data/`，不进 app，也不进知识库。
- 数据里只有师傅写下的数。

### 7. 调料仍按菜算（Terry 决定 4）

调料和主料一样，走第 3 条的三种出处，单位按第 4 条。

- **优先用规则。** 请师傅给常用调料定「每份大约多少」，例如盐、味精、鸡精、糖、生抽、老抽、蚝油、料酒、食用油，单位跟各自的基准单位走。需要的话，可以按做法再细分，炒菜、炖菜、凉菜各定一个数。49 道菜里出现在 2 道以上的食材名有 111 个，常用调料集中在其中十几种，定一次就能覆盖大部分调料行。
- **规则不合适的菜**，由师傅逐道给指定值或实称值。
- **「点、少许、一点点、来点」**：
  - 原话照旧留在 `originalAmount`。
  - 只有被规则覆盖、或者师傅给了指定值或实称值，这一行才有数。都没有的，继续写未知，采购页照旧显示「原用量未录」。
  - 不把「点」换成 0、1 或「适量」。只有来源原话就是「适量」时，才记为 `to-taste`（[team-meals 合同](../specs/team-meals-contract.md)第 61 行）。
- **炸油、过油用油**：记每份实际耗掉的量，不记锅里放了多少。「油宽点」「炸鸡用油」说的是锅里的量，不是要买的量。
- **水**：不是采购项。要不要放进标准食材目录，由 [#167](https://github.com/TERRYYYC/canteen-os/issues/167) 定。
- **对采购页的影响**：采购页对每种料分别判断能不能算（`team-meals.ts:241-257`）。调料还没补齐时，只有这几行显示「数量待定」，主料照常计算。整张清单的合计仍按 INV-8 标为不完整，不当成总量。

### 8. 这一轮只补最少的字段

**采购需要：**

- 份数，写 1。
- 每行每份的净料用量，单位按第 4 条。
- 绑定的标准食材。
- 按 g 或 ml 计的料要有净料率。
- 个数和重量之间要换算的料，要有每个多少克。

标准食材的目录、采购规格（供应商、包装、价格），以及怎么绑定，按 #167 的结论办。

**备料需要（主料）：**

- 切法：从 `data/techniques.json` 里已有的技法中选，记在 `prep.techniqueRef`。
- 大小：记在 `prep.size`。
- 准备时机：记在 `prep.timing`。
- 要提前多久，也就是腌、泡、卤、醒的时长。现有的 `prep` 只有 `techniqueRef`、`size`、`timing`、`note`、`image`，没有地方记时长。所以在 `prep` 下新加一个结构化的「提前时长」，写成数值加单位（分钟、小时、天），见 schema 那一行。
  - `prep.timing` 照旧只记什么时候准备（前一天、当天早上、开餐前）。
  - `prep.note` 只写别的说明，不再用来记时长。

**和第 11 条的对接**：师傅补了「提前时长」的新版本，对应的「提前多久没说」提示按第 11 条第 5 点处理。

**这一轮不补：** 火候、时长、出锅标准，留给菜品库以后补。

### 9. 先补什么

- **第一批**：主料已有重量的 7 道（Terry 决定 3）。
  - 这 7 道的原方重量按第 1 条只作参考。主料仍由师傅逐道给实称值或指定值，调料先用规则（#172）。
  - 这 7 道用到的标准食材和采购规格见 #173。
- **测试周要用的菜和常做的菜**：由师傅逐道补。
- **其他菜**：先用规则打底，师傅过一遍，改掉不合适的。

### 10. 和 ADR-0011、「未知写未知」的关系

- **复核仍在 app 外**，ADR-0011 的决定不变。补料也在 app 外进行：师傅在补料表上填，或者口述，再由 Claude 整理。
- **补好的用量写到哪：首批 7 道走知识库**（Terry 补充决定 1）。
  1. 先把 7 道从本机知识库同步到远端（#159）。
  2. 在知识库里补成新版本，包括食堂用量和出处（第 1、3 条），以及绑定的标准食材（#173）。
  3. 排菜时固定这一版（#172）。

  这些写入都在签收以后做。同步要排在本 ADR 签收之后，因为导入时要按第 1 条把原方和食堂用量分开存，还要按第 11 条保留「没说清」属于哪一步、哪样材料。如果先同步，之后还得再存一次新版本。
- **存成知识库新版本、排进菜单，都不等于厨房核定**（ADR-0011，`CONTRIBUTING.md:102`）。
- **出处写明的值不算「补数」。** 它是师傅的决定，数据里写明了出处。没有师傅的决定，就仍然是未知。当前工作合同第 49 行、`CONTRIBUTING.md:104`，以及 team-meals 合同的 INV-1、INV-7、INV-8 都不变。
- **公开范围。** 固定进 `data/` 的文件是公开资料（GitHub Pages）。规则和用量是厨房的做法，可以公开。视频链接、原片截图、原话以外的来源原文不进 `data/`，「没说清」的原话也不进（[ADR-0010](0010-knowledge-source-access.md)）。

**不在本 ADR 范围内的事：**

- 师傅能抽多少时间，用纸、表格还是口述。
- 标准食材的采购规格由谁填、在哪填。
- 菜谱食材绑定标准食材在哪做。

这三件按 #170 的安排，等 #167 的提案给出选项后再定。

### 11. 视频里没说清的地方，随固定版本带上类别和位置（并入自 #177）

Terry 补充决定 2 把 #168（D3）的 schema 决定并进了本 ADR。细节以 [D3 设计](https://github.com/TERRYYYC/canteen-os/blob/14fecd14a94317bebfece39c5da3e6a205498caa/docs/design/recipe-unknowns/README.md)为准，这里只记决定。

**1. 数据。**

- `dish` v3 加一个可选的顶层字段 `unknowns[]`。
- 每条只记类别（`kind`）和位置：第几步（`stepIndex`）或第几样材料（`componentIndex`）。两个都不带，就是整道菜的。
- 不记原话。原话留在私有知识库，只给师傅和管理员看（ADR-0010）。
- 没有条目时省略这个字段，不写空数组。
- 同一位置、同一类别只写一条。
- 位置越界的条目，固定时和校验时都拒绝（D3 设计 §2.2）。

**2. 类别：9 类，闭集。**

- `prep-ahead`：提前多久。另外记下要提前做的是哪件事：腌、泡、卤、醒、晾凉，还是别的。
- 其余 8 类：`amount`、`net-or-gross`、`cut-size`、`identity`、`heat`、`duration`、`doneness`、`other`。
- 9 类全部带进固定版本，按页面分开显示（D3 设计 §3）。
- 份数不设类别：`baseServings` 没填，就是没说。

**3. Worker。**

- 固定时，把知识库的步骤 ID、食材行 ID 换成位置。
- 知识库修订里没有条目，就不写这个字段。这样生成的文件和现在逐字节相同，旧版本重放的结果仍是「没有变化」（D3 设计 §6.2 C2）。
- 已经固定的版本不改写。旧字段 `sourceGapCount`、`evidence.unresolved` 只保留给旧资料读取，不换算成新字段（C1、C4）。

**4. 页面。**

- 统一用人话「……没说 · 问师傅」。
- 只写类别，不写条数，不显示 AI 原话，不出现「核对」「复核」「核定」「仍需」（ADR-0011 第 5 条）。
- **资料里已经有值，就不显示对应的提示；已经有提示的地方也不重复。** 这个判断只写在 `packages/web` 里的一个共用判断里。备料清单、备料页下方的做法、菜品页三处都调用它（D3 设计 §4.1）。
- 备料页只显示：提前多久、切多大、用量、毛重还是净重、用哪种。火候、做多久、做到什么样，只在菜品页显示（§3）。

**5. 和本 ADR 用量规则的接口。** D3 设计 §4.1 的表里，有两类要等本 ADR 定：

- `net-or-gross`：`qty` 一律是净料（第 4 条）。所以一样材料只要有带出处的 `qty`，就不显示「毛重还是净重没说」。
- `prep-ahead`：
  - 指向某样材料的条目：这样材料的 `prep` 里有提前时长（第 8 条），就不显示。
  - 只指向某一步的条目：页面判断不了。补料时，把提前时长记在被腌、被泡的那样材料上，同时在新版本里删掉对应的条目（D3 设计 K7）。

**6. 候选合同。**

- 「没说清」可以带类别和位置（D3 设计 §7 第 1 步）。
- 「审核后随固定版本进入备料提示」改成「存为菜谱后，随固定版本带上类别和位置」。

**7. 知识库要配合。**

- 按 D3 设计 §5 的 K1–K7。
- 已导入的 49 道只存新版本，不就地改（K6）。
- 分类只标出哪里没说，不补任何数值。

## Consequences

**好处：**

- 一套规则能让很多菜同时有数。
- 份数问题用一条规则就解决了。
- 原方的家庭量不会被误当成每份用量。
- 只要 #167 把采购规格补上，采购员就能看到主料要买多少。
- 帮厨在备料页能看到「腌多久没说 · 问师傅」这类提示；师傅补上以后，提示自动不再显示。

**代价：**

- 规则值和指定值是估算，单道菜会有偏差。以后可以靠「做完以后」的反馈（product-structure 第 102 行）换成实称值，这不在本轮。
- 按第 1 条，原方里已有的 155 行重量也不再直接进计算，要等师傅给出处之后，这些菜的采购才算得出来。这是有意的。
- 调料仍按菜算，486 行调料是补料工作里量最大的一块。规则没覆盖到的调料，采购页上会继续出现「原用量未录」。
- 私有知识库要配合的事变多了：
  - 原方和食堂用量分开存（第 1 条）；
  - 「没说清」的条目带上位置（第 11 条）。

  这两件不做，首批 7 道就没法按本 ADR 固定。
- schema 要新加这些可选字段：用量出处、原方结构化值、提前时长、`unknowns[]`、标准食材换算值的出处，另加规则文件。都按 schema → types → data → docs 的顺序同步。都是可选字段，不是破坏性变更。另外多两条校验：
  - 份数写 1 的菜，有数的 `qty` 必须有出处；
  - `unknowns` 的位置不能越界。

**不受影响的：**

- 采购引擎的计算公式。
- 已经固定的菜单版本：不改写，重放逐字节不变。
- 采购员自己的判断（待核对 / 待买 / 已有 / 已买）。

**签收后要同步的文档：**

- 当前工作合同第 49 行后面加两句：一句引用本 ADR 的用量规则；一句说明视频里没说清的地方随固定版本带上类别和位置，页面写「没说 · 问师傅」。
- `CONTRIBUTING.md:104` 加上引用。
- `schemas/dish.schema.json:21` 改 `baseServings` 的说明。`dish-v3.schema.json` 里 `sourceGapCount` 的说明，改成「旧字段，ADR-0011 后不再写入」。
- `skills/video-recipe-ingest/references/candidate-contract.md:9`、`:11`：按第 1 条和第 11 条第 6 点修改，见下表。
- `docs/design/team-meals-pages/D0-contract.md`：写进第 11 条的显示规则。
- 等 #165 合并后，在 `docs/video-import.md` 里写明补料表的用法。

## 签收时要定的

1. **规则放在哪：** `data/` 里的受控文件，还是 docs 里的一张表。推荐放 `data/`，这样每个规则值都能引用规则 id，也能做校验。
