# 内容级三语设计（zh / en / uk）

> **English summary.** CanteenOS implements content-level trilingualism, not just UI translation: every displayable entity (dish names, descriptions, ingredient names, recipe steps, comments) carries an `I18nString {zh, en, uk}` structure with at least one language present, resolved by the fallback chain zh → en → uk. Measurement units are stored as canonical internal symbols and localized only at display time. UI chrome strings are out of scope — clients use i18next. This design fills a real open-source gap: Mealie (42 UI languages) and Tandoor (37) translate only the interface while content stays monolingual (Mealie Discussion #5448).

- 关联决策：[ADR-0004](adr/0004-content-level-i18n.md)
- schema 定义：`schemas/common.schema.json` 的 `I18nString`

---

## 1. 为什么内容级三语是护城河

调研结论（[research/open-source-research-canteen-system.md](research/open-source-research-canteen-system.md) §五）：

- Mealie（42 个语言文件）与 Tandoor（37 个）**只翻译界面，不翻译内容**——食材库/菜谱名称是单语言字符串。Mealie 社区 Discussion #5448 明确抱怨 ingredients 只有英文。
- 食堂场景（尤其在乌中资企业/机构、乌克兰本地化食堂）里，**内容是用户数据**：菜品名、食材名、步骤说明、顾客评论都必须三语。
- 因此：**同一食材/菜品挂 zh/en/uk 三个名称**是我们的数据模型级要求，不是客户端 hack。

## 2. I18nString 契约

```json
{
  "zh": "番茄",
  "en": "Tomato",
  "uk": "Томат"
}
```

- schema：`common.schema.json#/$defs/I18nString`，`anyOf` 要求**至少一种语言**，`additionalProperties: false`（新增语言需改 schema，走 ADR）。
- 适用字段（规范要求，见 AGENTS.md 禁止事项 #3）：
  - Dish：`name`、`description`、`components[].note`、`steps[].instruction`
  - Ingredient：`name`
  - Supplier：`name`
  - MenuPlan：`name`
  - Feedback：`comment.translations`（评论见 §5）
  - DishPack：`manifest.suggestedDish.name`、`manifest.stepMapping[].instruction`

## 3. Fallback 链与展示规则

```
请求语言 = zh → zh，缺省退回 en，再缺省退回 uk
请求语言 = en → en，缺省退回 zh，再缺省退回 uk
请求语言 = uk → uk，缺省退回 zh，再缺省退回 en
```

即统一的主链为 **zh → en → uk**（zh 为主内容语言），展示层按"请求语言优先，沿主链兜底"实现。任何字段不得因缺翻译而展示空白。

伪代码：

```ts
function pick(s: I18nString, lang: Lang): string {
  const chain: Lang[] = [lang, "zh", "en", "uk"];
  for (const l of chain) if (s[l]) return s[l];
  throw new Error("I18nString invariant violated: empty");
}
```

## 4. 计量单位本地化

- **存储**：一律规范符号（`Unit` 枚举：`g/kg/ml/l/pcs/pack/tbsp/tsp/pinch`），不本地化。
- **换算**：跨单位通过 UnitConversion 表（食材专属优先，如鸡蛋 1 pcs = 55 g；全局兜底，如 1 kg = 1000 g）。
- **展示**：客户端按语言把符号映射为本地化文案，如：

| 符号 | zh | en | uk |
|---|---|---|---|
| g | 克 | g | г |
| kg | 千克 | kg | кг |
| ml | 毫升 | ml | мл |
| l | 升 | L | л |
| pcs | 个/枚 | pcs | шт |
| tbsp | 汤匙 | tbsp | ст. л. |
| tsp | 茶匙 | tsp | ч. л. |
| pinch | 一撮 | pinch | дрібка |

- 调研报告 §四"术语归一"建议：菜谱领域单位混乱是主要错误源，导入时过一层食材/单位词典映射（如 cup↔ml、тісто↔面团）。

## 5. 评论的三语存储（Feedback.comment）

评论是**用户生成内容**，与实体名称不同：

- `original`（必填）+ `originalLang`：存用户原文，永不被覆盖。
- `translations`（可选，I18nString）：机器翻译初稿 + 人工可修；**包含原文语言本身**（冗余但简化展示逻辑）。
- 缺失翻译时展示原文 + "机器翻译缺失"标记，不走 fallback 链冒充原文。

## 6. UI i18n（边界声明）

界面 chrome（按钮、表单标签、报错文案）**不在数据模型内**，客户端用 [i18next](https://www.i18next.com/) 自理。本仓库只约束内容数据的三语结构。

## 7. 开放问题（Open Questions）

1. 新增语言（如俄语、波兰语）的 schema 演进策略：直接扩 `I18nString` properties 还是改 map 结构？（当前决策：扩 properties + ADR，保持校验严格。）
2. 机器翻译供应商选择（评论翻译）：复用视频导入的 Gemini/Qwen 通道，还是独立服务？
3. dishpack 解析输出的三语名称质量未经验证——POC 时需重点实测乌克兰语（调研报告已标注"无公开 benchmark"）。
