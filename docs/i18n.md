# 内容级三语设计（zh / en / uk）

> **English summary.** CanteenOS implements content-level trilingualism, not just UI translation: every displayable entity (dish names, ingredient names, technique names, recipe steps) carries an `I18nString {zh, en, uk}` structure with at least one language present, resolved by the fallback chain zh → en → uk. **The data itself holds only the three plain translations** — translation provenance/status lives in a sidecar `translations.lock.json` (per-field `source_hash` + `status: machine|human`, maintained by a script; human-edited fields are never re-translated, per scenario H of the v2 research and ADR-0006). Measurement units are stored as canonical internal symbols and localized only at display time. UI chrome strings are out of scope — clients use i18next. This design fills a real open-source gap: Mealie (42 UI languages) and Tandoor (37) translate only the interface while content stays monolingual (Mealie Discussion #5448).

- 关联决策：[ADR-0004](adr/0004-content-level-i18n.md)、[ADR-0006](adr/0006-scope-reduction-v2.md)（翻译状态旁文件化）
- schema 定义：`schemas/common.schema.json` 的 `I18nString`

---

## 1. 为什么内容级三语是护城河

调研结论（[research/open-source-research-canteen-system.md](research/open-source-research-canteen-system.md) §五）：

- Mealie（42 个语言文件）与 Tandoor（37 个）**只翻译界面，不翻译内容**——食材库/菜谱名称是单语言字符串。Mealie 社区 Discussion #5448 明确抱怨 ingredients 只有英文。
- 食堂场景（尤其在乌中资企业/机构、乌克兰本地化食堂）里，**内容是用户数据**：菜品名、食材名、步骤说明、顾客评论都必须三语。
- 因此：**同一食材/菜品挂 zh/en/uk 三个名称**是我们的数据模型级要求，不是客户端 hack。

## 2. I18nString 契约

```json
{
  "zh": "番茄",
  "en": "Tomato",
  "uk": "Томат"
}
```

- schema：`common.schema.json#/$defs/I18nString`，`anyOf` 要求**至少一种语言**，`additionalProperties: false`（新增语言需改 schema，走 ADR）。
- 适用字段（规范要求，见 AGENTS.md 禁止事项 #3）：
  - Dish：`name`、`components[].prep.note`、`steps[].text`
  - Ingredient：`name`
  - Technique：`name`、`note`
  - MenuPlan：`name`

## 3. Fallback 链与展示规则

```
请求语言 = zh → zh，缺省退回 en，再缺省退回 uk
请求语言 = en → en，缺省退回 zh，再缺省退回 uk
请求语言 = uk → uk，缺省退回 zh，再缺省退回 en
```

即统一的主链为 **zh → en → uk**（zh 为主内容语言），展示层按"请求语言优先，沿主链兜底"实现。任何字段不得因缺翻译而展示空白。

伪代码：

```ts
function pick(s: I18nString, lang: Lang): string {
  const chain: Lang[] = [lang, "zh", "en", "uk"];
  for (const l of chain) if (s[l]) return s[l];
  throw new Error("I18nString invariant violated: empty");
}
```

## 4. 计量单位本地化

- **存储**：一律规范符号（`Unit` 枚举：`g/kg/ml/l/pcs/pack/tbsp/tsp/pinch`），不本地化。
- **换算**（ADR-0006 收窄）：`g↔kg`、`ml↔l` 是代码常量；`pcs↔g` 只靠 `ingredient.pcsToGram`（如鸡蛋 1 pcs = 55 g）——无独立换算实体，换算失败进人工确认，引擎不猜测。
- **展示**：客户端按语言把符号映射为本地化文案，如：

| 符号 | zh | en | uk |
|---|---|---|---|
| g | 克 | g | г |
| kg | 千克 | kg | кг |
| ml | 毫升 | ml | мл |
| l | 升 | L | л |
| pcs | 个/枚 | pcs | шт |
| tbsp | 汤匙 | tbsp | ст. л. |
| tsp | 茶匙 | tsp | ч. л. |
| pinch | 一撮 | pinch | дрібка |

- 调研报告 §四"术语归一"建议：菜谱领域单位混乱是主要错误源，导入时过一层食材/单位词典映射（如 cup↔ml、тісто↔面团）。

## 5. 翻译状态管理：translations.lock.json 旁文件（ADR-0006）

**数据本体只有 `{zh, en, uk}` 纯文本**；翻译是"机翻初稿 + 实践中人工修"（场景 H），状态不污染数据本体，由脚本 `scripts/translate.mjs` 维护在旁文件 `data/translations.lock.json`（格式与规则的完整说明见 §6，此处只给概念）：

```json
{
  "data/techniques.json#/21/name": {
    "source_hash": "…（zh 原文的 sha1，40 位十六进制）",
    "status": "human",
    "updatedAt": "2026-09-07T00:00:00.000Z"
  },
  "data/dishes/tomato-egg-stir-fry.json#/steps/0/text": {
    "source_hash": "…",
    "status": "machine",
    "updatedAt": "2026-09-07T00:00:00.000Z"
  }
}
```

规则（场景 H 推荐工作流落地）：

- 键 = `<相对文件路径>#<RFC 6901 JSON pointer>`，一条 I18nString 一个键（en/uk 共用一个状态）；`source_hash` 记录翻译时 zh 源文的 sha1，`status ∈ machine | human`。
- 机翻脚本只处理"缺失的 en/uk，或 source_hash 变了且 status = machine"的字段；**人工改过的译文永不被覆盖**，zh 变了只标 `stale: true` 提示人工。
- 技法词表（`data/techniques.json`）是机翻的术语硬约束 glossary：先查表命中直接用、不命中才送 API，输出后脚本回查术语一致性（"焯水"永远翻成同一个词）。
- 引擎首选 DeepL API（Free 档起步）+ Glossary v3；长文本可用 Gemini/GPT，但术语遵从是概率性的，必须保留输出回查。uk 无现成菜名对照表，以 en 为枢轴自建。
- 锁文件与数据本体的漂移（文件删了键还在等）由脚本按"孤儿键"报告并在默认模式下清理（§6）。

注：顾客评论（原文+三语翻译存储）属于 deferred 的模块三，恢复时沿用"原文永不覆盖、翻译可修"的同一原则。

## 6. 翻译状态旁文件 translations.lock.json：规则与命令

实现：`scripts/translate.mjs`（纯 Node ≥ 20，零依赖，ESM；测试 `scripts/translate.test.mjs`）。数据契约来自 `docs/execution-brief.md` §1.6 与 §5「翻译锁」。

### 6.1 文件格式

位置 `data/translations.lock.json`，键按字典序排列，2 空格缩进，末尾换行：

```json
{
  "<file>#<pointer>": {
    "source_hash": "sha1(zh) 十六进制",
    "status": "machine | human",
    "updatedAt": "ISO 8601",
    "stale": true
  }
}
```

- `<file>`：相对仓库根目录的路径，如 `data/dishes/tomato-egg-stir-fry.json`。
- `<pointer>`：RFC 6901 JSON pointer，指向整个 I18nString 对象（不到语言一级），如 `/steps/0/text`、`/components/0/prep/note`、techniques 里的 `/21/name`。
- I18nString 的识别规则：对象含 `zh` 键且值为字符串；`data/**/*.json` 全部扫描（含 `techniques.json`，排除 lock 本身）。没有 `zh` 的对象不会被识别（zh 是唯一机翻源）。
- `stale` 只出现在 `status: human` 且当前 zh 的 sha1 ≠ `source_hash` 的条目上；其他情况下该键不存在。
- 该文件不是实体，不受 `schemas/` 校验（两个校验脚本按显式目录/文件清单工作，见 `scripts/validate-schemas.mjs` 的 `DATA_TARGETS`）。

### 6.2 状态机

| 现状 | lock 记录 | 脚本动作 |
|---|---|---|
| en/uk 至少其一存在 | 无 | 保守视为人工：写入 `status: human`；缺的那一种语言仍会机翻补上（status 不变） |
| en/uk 全缺 | 无 | 机翻两种语言，成功后写入 `status: machine`；无 key 时只计入缺失统计，不入 lock |
| zh 未变 | `machine` | 只补缺失语言 |
| zh 变了 | `machine` | en、uk 全部重翻，`source_hash` 更新为新 zh 的 sha1 |
| zh 未变 | `human` | 只补缺失语言；若之前有 `stale` 则清除（zh 恢复原文） |
| zh 变了 | `human` | **不覆盖任何已有译文**，标 `stale: true`，报告里打印新旧 sha1；缺失语言仍补 |
| 键在 data/ 里已不存在 | 任意 | 报告为"孤儿"，默认模式下从 lock 移除 |

人工校对流程：看到 `stale` 的条目，手改 JSON 里的 en/uk 后，把该条 lock 的 `source_hash` 改成报告里打印的新 sha1（或直接删除该条让脚本下次重新采集为 human），再跑一次脚本 `stale` 即消失。想把某条机翻"转正"为人工，把 `status` 改成 `human` 即可，此后永不被覆盖。

### 6.3 机翻后端与术语表

- 环境变量 `DEEPL_API_KEY`：有则调用 DeepL（key 以 `:fx` 结尾走 `api-free.deepl.com`，否则 `api.deepl.com`），`source_lang: ZH`，`target_lang: EN-US / UK`，每批 ≤ 50 条，429/5xx 重试 3 次。**没有 key 不报错**：打印缺失统计（按文件、按语言）、只写 lock 的 human 采集、`exit 0`，CI 可直接跑。
- 术语表：由 `data/techniques.json` 每条 `name.zh → name.en / name.uk` 自动生成（只取 name，不取 note），优先上传为一个 DeepL **v3 多语 glossary**（按内容哈希命名、同名复用不重复创建）；v3 不可用时退回 v2（每语言一个）；都失败则不带术语表翻译并打印提示。
- 翻译逻辑可注入：`import { runTranslate } from "./scripts/translate.mjs"`，`runTranslate({ files, lock, translator })`，`translator = { name, translate(texts, lang) → Promise<string[]> }`；`translator = null` 即"只统计、只采集 human"。

### 6.4 命令

```bash
npm run translate:dry      # = node scripts/translate.mjs --dry-run：列出待翻条目与预估字符数，不写任何文件
node scripts/translate.mjs --check   # 只报告（缺失 / stale / 待重翻 / 孤儿），不写任何文件，exit 0
npm run translate          # = node scripts/translate.mjs：有 key 机翻并写回 data/ + lock；无 key 只写 lock
npm run test:scripts       # = node --test scripts/*.test.mjs
```

写回数据文件时用 `JSON.stringify(data, null, 2)` + 末尾换行，只写实际收到译文的文件；键序整理为 `zh, en, uk`。手工紧凑排版的文件（如 `techniques.json` 的单行 I18nString）一旦被写回会展开为标准 2 空格排版。

## 7. UI i18n（边界声明）

界面 chrome（按钮、表单标签、报错文案）**不在数据模型内**，客户端用 [i18next](https://www.i18next.com/) 自理。本仓库只约束内容数据的三语结构。
