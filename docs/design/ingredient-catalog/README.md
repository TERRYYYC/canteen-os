# 标准食材层：目录、采购规格与菜谱食材的绑定

> **状态：已签收（2026-10-19）。** Terry 10/19 签收，§9 的 C1–C9 全部按推荐（[#170](https://github.com/TERRYYYC/canteen-os/issues/170#issuecomment-6258259363)）。本文回答 [#167](https://github.com/TERRYYYC/canteen-os/issues/167) 的 6 个问题。它本身不改变[当前工作合同](../../current-contract.md)、schema 和代码，也没有写任何知识库（本机或远端）；按「先改合同、再实施」，实施按 §8 列的 issue 走。签收是对设计内容的决定；本文所在的 PR 合并前，还要在最新 HEAD 上做非作者审查。计划和顺序见 [#170](https://github.com/TERRYYYC/canteen-os/issues/170)。

> 附件：[候选目录表](candidate-catalog.md)（从 49 道菜统计，只有食材名和次数）；归组建议 [groups.json](groups.json)；统计脚本 [catalog-stats.mjs](catalog-stats.mjs) 和它的测试（§10）。

## 0. 一页看完

**现状**（#170 的 10/19 只读盘点）：49 道收藏菜谱、867 行食材，绑定了标准食材的 0 行；知识库里的标准食材只有 5 种演示条目。用一道真菜在内存里试跑，采购 21 行全部算不出来。

**断在哪里**：代码这一层是通的（[#125](https://github.com/TERRYYYC/canteen-os/issues/125) 做完了），缺的是数据和录入流程。没绑定的行，固定时只带名称，没有基准单位和采购规格；同一种料在不同菜里也永远合不成一行（§1）。

**结论**（Terry 10/19 签收，全部按推荐；每一条在后文都给了选项）：

1. **目录分批建。** 49 道菜的食材名归成 220 种候选标准食材（主料 107、调料 113）。先建首批 7 道菜用到的 61 种，再补出现在 2 道以上的；只在一道菜里出现的，等那道菜要排时再建。水不是采购项，菜里自制的东西不进目录。有 26 组名称要先认是什么再绑，其中「葱」18 道没说大葱还是小葱，「牛肉」7 道没说部位。
2. **首批走知识库（Terry 10/19 已定，[#170](https://github.com/TERRYYYC/canteen-os/issues/170#issuecomment-6257683642)）。** 「首批直接写 Git 数据」也列成了选项，但没选：Git 这条路的菜不在知识库里，以后还要再录一遍。知识库这条路要先把 7 道从本机同步到远端（[#159](https://github.com/TERRYYYC/canteen-os/issues/159)），排在知识库配合改造 [#182](https://github.com/TERRYYYC/canteen-os/issues/182) 之后（§8）。写入都放在第 2 波、设计签收以后。
3. **字段基本够，缺 5 样**：类别、包装叫法（箱、袋，三语）、参考价是哪天的、别名（知识库里有这个字段，编辑器没有输入框）、按师傅规则填的值的出处（#170 决定 2 要求写明）。另外，按 g、ml 计的料必须有净料率，盐、油也要明写 1。
4. **知识库来的菜有一个结构问题。** 这些菜的采购规格跟着菜谱一起固定。改一次价，新旧菜里同一种料的版本就不同，这种料就算不出来。首批走知识库，所以这个问题首批也有。目标是把采购规格从菜谱固定里拿出来、跟着采购单走，这要写 ADR。每版只开一篇 ADR，ADR-0012 进下一版（先收 alpha.5），所以采购这篇排在ADR-0012 之后的那一版。在那之前：先把规格填好再固定菜，测试期间不改价（C4）。
5. **谁填、在哪填。** 净料率、每个多少克、主料还是调料由师傅定；采购规格由采购员给。两样都在 app 外用表格确认，和 ADR-0011 一致。「在哪」是知识库；由 Terry（或有管理员令牌的人）照表在师傅后台现有的标准食材编辑器里录入（C3）。不用给采购员开知识库写权限。
6. **怎么绑。** 按名字给建议，由人确认，不自动合并。绑定建议印在 [#169](https://github.com/TERRYYYC/canteen-os/issues/169) 的补料表上，师傅补用量时一起勾。首批 7 道在现有菜谱编辑器里逐行选，下拉要去掉版本号和编号（[#183](https://github.com/TERRYYYC/canteen-os/issues/183)）。49 道全量等批量写入工具（C5）。
7. **采购怎么用。** 调料按菜算已经定了（#170 决定 4），所以调料同样要绑定，要有基准单位、净料率和采购规格。部分缺量时先不算已知部分，保持现行合同，首批跑完再看（C7，[#175](https://github.com/TERRYYYC/canteen-os/issues/175)）。水建一个不带采购规格的条目，采购单上只出一行；但这样只要排了有水的菜，合计就一直不完整。「不用买」标记要改 schema，和第 4 条写进同一篇 ADR，排在ADR-0012 之后的那一版；在那之前接受这一点（C6、C8）。

Terry 10/19 定下的 9 件事见 [§9](#9-terry-定下的)。

## 1. 现状：链路在哪里断

**绑定存在哪。** 菜谱每行食材有一个可选的 `ingredientId`（[knowledge-types.ts:4](../../../packages/web/src/api/knowledge-types.ts)），指向知识库里的一种标准食材。固定菜谱时（[knowledge-materialization.ts:57-62](../../../packages/worker/src/knowledge-materialization.ts)）：

- 绑了的行：把这种标准食材当时那一版的全部字段（别名除外）写成这道菜的食材文件，带上 `canonicalIngredientId` 和版本号。
- 没绑的行：食材文件里只有名称、`trackStock: false` 和角色。没有基准单位，也没有采购规格。

**跨菜合并。** core 按 `canonicalIngredientId` 把不同菜里的同一种料合成一行。没绑的行按「菜谱 + 行」各算一行，同名也不合并（[team-meals.ts:70-75](../../../packages/core/src/team-meals.ts)）。这是合同要求的：跨菜合并只认人明确绑定的身份，不按同名字符串合并（[当前工作合同](../../current-contract.md)「数据和状态的各自真源」）。

**一种料什么时候能算出采购量**（[team-meals.ts:241-257](../../../packages/core/src/team-meals.ts)）。下面任何一条不满足，这种料整行显示「数量待定」，并写出原因（[purchase-list.ts:41-48](../../../packages/web/src/pages/purchase-list.ts)）：

| 要什么 | 记在哪 | 缺了采购页显示 |
|---|---|---|
| 采购规格：供应商、每包多少、包装单位 | 标准食材 | 采购规格未录 |
| 基准单位 g、ml 或 pcs | 标准食材 | 标准材料的基准单位未录 |
| 净料率（按 g、ml 计的料） | 标准食材 | 标准材料的净料率未知，请人工判断采购量 |
| 每道菜这一行的用量，能换算成基准单位 | 菜谱 | 原用量未录 / 单位不能换算 |
| 配方份数、计划份数 | 菜谱、计划 | 配方基准份数未录 / 计划份数未录 |
| 所有菜固定的这种料是同一版规格 | 固定资料 | 同一材料的采购规格版本不同，请核对后分别估算 |

单位只换 g↔kg、ml↔l；个数和克之间靠「每个多少克」；体积和重量之间、勺和克之间都不换（[engine.ts:160-166](../../../packages/core/src/procurement/engine.ts)）。

**已固定的不会被改。** 同一个菜谱版本固定过一次，就不能用别的依赖再固定一遍，Worker 会报冲突（[write.ts:116](../../../packages/worker/src/write.ts)）。所以给已经排过的菜补绑定，要在知识库里存出新版本，排菜时换用新版本（[ADR-0011](../../adr/0011-recipe-review-outside-app.md) 第 3 条）。

**录入入口已经有。** 师傅后台的菜谱编辑页有「标准材料与技法」一块，能新建、编辑标准食材，每次保存出一个新版本；每行食材下面有「共享标准材料（明确绑定 ID）」下拉（[adoption.ts:86、110](../../../packages/web/src/pages/admin/knowledge/adoption.ts)）。下拉里每一项显示「名称 · v版本 · 编号前 8 位」，没有按名字的建议。

**还有一种菜：直接写进 Git 的菜。** 上面说的都是知识库来的菜。直接写进 Git 的菜（现在的演示菜就是）每行食材的 `ingredientRef` 直接指向 `data/ingredients/` 里的一个文件。几道菜指向同一个文件，core 就按这个 ref 合成一行（[team-meals.ts:75](../../../packages/core/src/team-meals.ts)）。改价就是改这个文件。发布按 Git 提交固定，已保存的采购单按自己的来源版本读，所以没有 §3.3 的版本冲突。`data/ingredients/` 现在有 9 个演示文件，带的是演示用的供应商和价格（例如食盐）。演示菜和测试都在用这些文件。

**49 道现在在哪。** 这 49 道只在本机知识库，还没同步到远端，远端只有其中 3 条（[#159](https://github.com/TERRYYYC/canteen-os/issues/159)）。师傅后台连的是远端，首批这 7 道要先同步过去，才能在编辑器里绑定。调度 10/19 复核时，编辑器里没有这 7 道；本文没有读远端。Terry 10/19 定了首批 7 道走知识库，写入放在第 2 波、对应设计签收以后（[#170](https://github.com/TERRYYYC/canteen-os/issues/170#issuecomment-6257683642)）。

## 2. 问题 1：目录从哪来

### 2.1 数据和口径

只读收藏解析结果的 `candidate.json`：2026-10-01 批 5 道、2026-10-03 批 44 道，共 49 道菜、867 行。

- 名称原样 436 个。很多名称带括注，写的是用途或疑问，例如「（煮料）」「（身份待核）」，不是食材身份。
- 去掉括注后 394 个，其中出现在 2 道以上的 111 个。
- #167 里写的「391 个名称、盐 28 道」来自另一次盘点，口径略有不同。本文的数都能用脚本复跑（§10）。按本文口径，「盐」出现在 27 道；和咸盐、熬汤盐等归成「食盐」一组后是 31 道。

### 2.2 归组规则（建议）

1. **去掉括注**再比较。
2. **切法、形状不是新食材**：姜丝、姜片、姜米 → 生姜；胡萝卜丁 → 胡萝卜；干辣椒丝、干辣椒段 → 干辣椒。
3. **用途前缀不是新食材**：炸鸡用油、滑油用食用油 → 食用油；后续补调盐、熬汤盐 → 食盐。
4. **各地叫法合并**：大茴、大料 → 八角；西红柿 → 番茄；芝麻油 → 香油；大油 → 猪油；蒜苔 → 蒜薹；鸡脯肉 → 鸡胸肉；花椒面 → 花椒粉。
5. **品牌不单建**：海天金标生抽 → 生抽；水塔陈醋 → 陈醋。品牌写进采购规格。用途确实不同的品牌产品（例如鸡饭老抽）先单列，由师傅定。
6. **部位、品种、整碎不同，采购就不同的，不合并**：牛腩和牛里脊；带骨鸡腿和去骨鸡腿肉；花椒和青花椒；花椒和花椒粉。
7. **一行写了两种料的拆开**：「盐、糖」「青红椒」「黑白胡椒粉」两边都计；补菜时拆成两行。
8. **水不是采购项**，不填采购规格（采购单上怎么只出一行见 §6.3）。**菜里自制的不进目录**：高汤、料油、芡汁、混合酱，它们的原料另有行。
9. **先认是什么，认清前不绑定，也不给名字建议**：
   - 没说大葱还是小葱的「葱」；
   - 没说部位的「牛肉」「鸡肉」；
   - 没说肉种的「后腿肉」「肉丝」；
   - 没说鱼种的「整鱼」「鱼片」；
   - 画面识别出来、名称待核的料。

**同名不同物**靠第 6、9 条处理。「葱」「青椒」「生粉」「胡椒粉」「酱油」各地所指不同。表里给了最常见的归法，但都写了「师傅确认」，绑定前要看那道菜。

## 3. 问题 2：每种标准食材要哪些字段

### 3.2 几个容易漏的

- **净料率不能空。** 按 g、ml 计的料没有净料率就算不出来（[team-meals.ts:245](../../../packages/core/src/team-meals.ts)）。盐、油、糖这类没有损耗的料，也要明写 1。按个数计的料（鸡蛋）不设净料率，要设每个多少克，才能和按克写的用量互换。
- **单位要对齐。** 生抽按 ml 买，菜里写「20 克」，换不了。#169 的草稿请师傅按 g 或 ml 给每份用量。建议基准单位跟着采购单位走：液体用 ml，其余用 g，按个买的用 pcs；师傅定规则时用同一个单位。这样暂时不用加密度和「每勺多少克」。
- **角色只有两种。** 葱、姜、蒜、香菜要切，按「主料」处理，备料页才会提示切法。是否加第三种（例如「配料」）要改 schema，这次不提。
- **先不填现有量。** 现有量改一次，标准食材就出一个新版本，会引出 §3.3 的冲突。「已经有了」由采购员在采购单上判断（现有的「已有」）。

### 3.3 一个要先定的结构问题：采购规格跟谁一起固定

这一节只说知识库来的菜。首批走知识库，所以首批也有这个问题。直接写进 Git 的菜没有这个问题（§1）。

**现在的做法。** 知识库来的菜固定时，标准食材的全部字段（包括供应商、包装、参考价、现有量）随这一版菜谱一起固定。估算时，同一种料在本次范围内的所有菜里规格必须一样，比较的内容包括供应商、包装、参考价和现有量；不一样就整行不算（[team-meals.ts:129-134、246](../../../packages/core/src/team-meals.ts)）。

**会出什么事。** 第 43 周固定了 7 道菜，用的是食盐第 1 版。第 44 周采购员改了参考价，食盐变成第 2 版，第 44 周新固定的菜用第 2 版。如果第 44 周的菜单里同时有旧菜和新菜，食盐这一行就显示「同一材料的采购规格版本不同」，算不出来。要消掉冲突，得把每道旧菜都存出新版本，再在排菜时换过来。价格每周都可能变，这个代价很高。

| 选项 | 怎么做 | 好处 | 代价 |
|---|---|---|---|
| A. 维持现状 | 采购规格还在标准食材里，随菜谱固定；规矩是先填规格再固定，改价时整批出新版本 | 不改代码 | 改价很重，实际上价格会被冻住 |
| B. 采购规格单独固定 | 标准食材里只留身份和厨房换算（名称、别名、基准单位、每个多少克、净料率、角色），随菜谱固定。供应商、包装、参考价放进一张单独的采购规格表，按标准食材挂；发布时写进发布资料，采购单按它自己的来源版本（basis）读 | 改价不碰菜谱，旧采购单不变 | 要写 ADR，改合同、schema、core 和 Worker |
| C. 估算时取最新的规格 | 同一种料版本不同时，用最新那一版的采购规格 | 改动小 | 违反「固定版本不偷偷换」，不建议 |

**推荐：目标是 B（已定，§9 C4）。** B 要写 ADR。每版只开一篇 ADR；Terry 定了先收 alpha.5，ADR-0012 进下一版，采购这篇排在ADR-0012 之后的那一版（[#170](https://github.com/TERRYYYC/canteen-os/issues/170#issuecomment-6258259363)）。在那之前用 A：

- 首批 61 种先把采购规格填好，再固定菜；
- 测试期间不改价；
- 真要改价，就把用到这种料的菜整批存出新版本，排菜时一起换过来。

B 做的事和 Git 菜现在的样子一样：规格跟着发布走，不跟着菜谱走。

## 5. 问题 4：怎么绑定

### 5.1 规则

- 绑定就是给菜谱的某一行选一种标准食材。存下来是这道菜的新版本；已经固定、已经排进菜单的版本不变（§1）。
- 名字只用来给建议，不自动绑。去掉括注后的名称和标准食材的名称或别名完全一样，才给建议。「先认是什么」的名称不给建议。名称带待核标注的（附表里的 †），建议旁边要写「名称待核」。
- 一行写了两种料的，先拆成两行再绑。
- 水和自制的料怎么处理，见 §6.3。

### 5.2 在哪绑

| 选项 | 怎么做 | 好处 | 代价 |
|---|---|---|---|
| A. 现有菜谱编辑器逐行选 | 已经有，每行一个下拉 | 不用开发 | 下拉显示版本号和编号，没有建议；49 道 867 行太慢 |
| B. 表格加写入工具 | 一行菜谱食材一行：菜名、原名、建议、确认；确认后由工具写进知识库，每道菜存一个新版本 | 适合全量；可以和补料表合在一起 | 要新做工具，要写知识库 |
| C. 按食材绑的新页面 | 选「食盐」，列出所有叫盐、咸盐、熬汤盐且没绑的行，勾选后保存 | 一次绑一种料，最快 | 要新做页面 |

## 6. 问题 5：采购怎么用

### 6.1 调料仍按菜算（#170 决定 4）的影响

调料不改成「常备调料，看库存补」，已经定了。影响：

- **调料也要绑定**，也要有基准单位、净料率（多数是 1）和采购规格。首批 61 种里调料 41 种；首批 130 行里调料 87 行、主料 32 行（按本文的分法，葱姜蒜算主料）。首批的工作量主要在调料。
- **调料是大头。** 建议目录里调料 113 种、487 行；主料 107 种、276 行。
- **「勺、少许」换不了。** 只有按 #169 的师傅规则给了 g 或 ml 的行能算。规则没覆盖到的，这种料整行「数量待定」。
- **炸油、过油用油**按 #169 的草稿记每份实际耗多少油。它们和其他食用油绑到同一种标准食材，采购单上合成一行。

### 6.2 部分缺量时要不要先算已知部分

现在：同一种料只要有一道菜缺量，这种料整行不算，不给已知部分的数量、包数和金额（[小团队餐食终态合同](../../specs/team-meals-contract.md) §4、INV-8）。

| 选项 | 采购员看到 | 代价 |
|---|---|---|
| A. 维持现状 | 「数量待定」，加上缺什么 | 不改合同；有一道菜缺量，整种料都没数 |
| B. 给已知部分的下限 | 「已知部分至少 3 kg，另有 1 道菜没写量」；不算包数和金额，不进合计 | 要改合同 INV-8 和 core 的估算输出 |
| C. 按菜分行 | 同一种料按菜各列一行，有量的算 | 失去跨菜合并，和本提案的目的相反 |

**推荐 A，首批跑完再看（已定，§9 C7；讨论在 [#175](https://github.com/TERRYYYC/canteen-os/issues/175)）。** 首批 7 道的主料由师傅逐道实补，调料用规则补，部分缺量应当不多。如果首批跑下来，「数量待定」大多是因为一两道菜缺量，再开合同修订做 B。B 用的文案先备好：

| 中文 | English | Українська |
|---|---|---|
| 已知部分至少 {qty}，另有 {n} 道菜没写量 | Known part at least {qty}; dishes without an amount: {n} | Відома частина щонайменше {qty}; страв без кількості: {n} |

### 6.3 水和自制的料在采购单上

现在：没绑定的每一行都会进采购单（合同要求已录的食材全部进人工采购清单）。水在 35 道菜里都有，排了几道就出几行「水 · 采购规格未录」。

还有一个后果：只要有一种料算不出来，这张清单的合计就是「不完整」（[team-meals.ts:283-285](../../../packages/core/src/team-meals.ts)）。没有采购规格的水永远算不出来，所以只要排了有水的菜，即使其他料都齐了，合计也不完整。采购页上，水落在「未指定供应商」那一段，记为「数量待定，未计入小计」。菜里自制的 15 行（11 道菜）也一样。

| 选项 | 怎么做 | 采购员看到 | 合计 | 代价 |
|---|---|---|---|---|
| A. 不绑 | 维持现状 | 每道菜一行水 | 一直不完整 | 噪音多 |
| B. 建一个「水」条目，所有水行都绑上 | 不填采购规格，不算进目录的采购项 | 只有一行水，标一次「已有」 | 一直不完整 | 这一行仍写「采购规格未录」 |
| C. 加「不用买」标记 | 标准食材上加一个标记，采购单不列，估算也不算它 | 看不到水 | 水不再拖累合计 | 要改合同和 schema，要写 ADR |

**已定（§9 C6、C8）：现在用 B，让水只出一行。C 和 §3.3 的 B 写进同一篇 ADR，类别、包装叫法也在那次一起改，排在ADR-0012 之后的那一版。** 在那之前明确接受：只要排了有水的菜，合计就一直不完整。49 道里有 35 道用到水，几乎每周都会这样。

菜里自制的料（高汤、料油、芡汁、混合酱，11 道菜 15 行）不建标准食材，现在也不绑；采购单上各占一行，采购员标「已有」。它们的原料在同一道菜里另有行，照常绑定。C 如果只做成标准食材上的标记，自制品要么各建一个标「不用买」的条目，要么在菜谱行上另加标记，跟 C 一起定。师傅补菜时如果觉得哪一样其实是买现成的（例如红油、皮冻），改成正常的标准食材。

C 如果做，采购单上要有的文案：

| 中文 | English | Українська |
|---|---|---|
| 不用买 | No need to buy | Купувати не потрібно |

### 6.4 改价引起的冲突

见 §3.3。首批走知识库，这个冲突对首批也成立。ADR-0012 之后的那一版的采购 ADR 落地之前，测试期间不改已固定食材的采购规格；真要改，就把用到它的菜整批存出新版本再排。

## 10. 候选目录表和脚本

- [candidate-catalog.md](candidate-catalog.md)：由脚本生成，不要手改。只有食材名和次数，没有菜名、作者、视频链接、原话和本机路径。
- [groups.json](groups.json)：归组建议，人改这里。名称写去掉括注后的样子；一个名称出现在两个组里，表示「一行写了两种料，要拆」。
- [catalog-stats.mjs](catalog-stats.mjs)：读批次结果表 `RESULTS.md` 里分类为「菜谱候选」的行，顺着「来源」链接找到每道菜目录下的 `candidate.json`，只取食材名。链接找不到时，按「批次目录 / 作品编号」在同级目录里找（5 道复用菜在上一批的目录下）。
- 首批那一列要多给一个本机文件，每行一个作品编号。这个文件不入库。

复跑（在仓库根目录；`<批次目录>` 是 2026-10-03 那一批，`<首批编号文件>` 可省略）：

```bash
node docs/design/ingredient-catalog/catalog-stats.mjs --results <批次目录>/RESULTS.md --focus <首批编号文件>
```

核对仓库里的表和数据是否一致（一致时退出码 0）：

```bash
node docs/design/ingredient-catalog/catalog-stats.mjs --results <批次目录>/RESULTS.md --focus <首批编号文件> --check
```

脚本自己的测试只用临时造的数据，不需要私有数据：

```bash
node --test docs/design/ingredient-catalog/catalog-stats.test.mjs
```
