# 四条线 · 第二轮设计提案

> **状态：提案，未签收。** 本文不改变[当前工作合同](../../current-contract.md)和 [D0 页面合同](../team-meals-pages/D0-contract.md)，也不说明任何页面已经实现。与现行合同冲突的地方都列在下文，要先由 Terry 决定，再按“先改合同、再实施”的规则处理。
>
> 页面稿和组件在 Terry 的 claude.ai 上的 CanteenOS 设计系统里（v12，版本 `1791585029-5922`；21 张页面稿，每屏中文、English、Українська 并排；搪瓷蓝浅色单一配色，同 [PR #135](https://github.com/TERRYYYC/canteen-os/pull/135)）：<https://claude.ai/artifact/Dgn8Hu33WfMBj4LJkWhnph>。设计系统本身是私有的，匿名打开显示“Page not found”。21 张页面稿按 v12 导出的图片在 [screens/](screens/README.md)，可以独立核对；文字依据是本文和 [product-structure.md](product-structure.md)（设计系统里 `project/product.md` 同一版本的导出）。**页面稿仍是提案，不作为验收或实施依据。**

## 1. 为什么提

v0.3.0-alpha 打结时 Owner 说“不喜欢”（见 [调度日志](../../field-test/log.md) 2026-09-10、09-11）。之后他明确了两条要求：

- 所有内容只围绕师傅、帮厨、采购和菜品；
- 他们看不懂的、开发用的东西，都不放在他们眼前（版本号、提交号、编号、字段名、原始数据、可信度数字）。

本提案把厨房里的工作拆成四条线，每条线最多两层（列表 → 详情）。

## 2. 四条线

| 线 | 谁用 | 回答什么 | 页面稿 |
|---|---|---|---|
| 1 今日备料 | 帮厨（默认乌语） | 今天做哪几道菜；每道菜要准备什么、多少、怎么切；看不懂就问这一项 | TodayPrep · DishPrep · PrepItem · AskChef · CutTerms · CutSpec |
| 2 一周排菜 | 师傅 | 这周每天每餐做什么；怎样每天每周都不重样 | WeekPlan · DishPicker · WeekPlanDesktop · PlanEntry |
| 3 本周采购 | 采购员 | 这周要买什么、多少；拿着能不能直接下单 | WeeklyShopping · OrderCopy · IngredientDetail · ShoppingItem |
| 4 菜品库 | 师傅（帮厨可看已发布的） | 像菜单一样翻菜，像教学 App 一样看做法；我们厨房改过什么 | DishLibrary · DishPage · RecipeChanges · AfterService · DishCard |

三条原则：

1. **两种语言是两个人一起干活的工具。** 同一项备料，帮厨和师傅各用自己的手机，看到同样四样（食材、数量、切法、用于哪道菜），每样下面一行是对方的语言。
2. **采购清单按采购员实际下单的方式组织。** 采购员按食材类别买（蔬菜一处、肉蛋鱼一处、粮油调料一处）。判断标准是：拿着它能不能直接下单，还要不要另抄一遍。
3. **菜品库慢慢变成“我们厨房的菜谱”。** 保留原视频清楚的教学结构，记下师傅实际改过的用量、做法和注意事项，下次排到时用师傅确认过的版本。

## 3. 和现行合同对得上的（可以直接沿用）

- 未知就写未知：“还没写怎么切 · 问师傅”“用量没写”，不补 1、0 或“适量”。
- 保存和发布分开，状态写成人话（“已保存，还没发布”“帮厨和采购现在看到的是今天 9:40 发布的安排”）。
- 公开菜单、备料和无后台时的只读采购，读取同一次发布的固定资料；已保存的采购单按它自己的来源版本（basis）读取，换到新的发布要显式复核并保存。
- 备料按时机分组：前一天 → 早上 → 出餐前 → 调料备在手边（沿用现有 `prep.timing`）。
- 帮厨默认乌语，语言顺序 UA · 中 · EN；三种语言都要成立。
- 图片的几种状态（加载中、加载失败、没有照片、使用权待确认、外部图片未固定）和现有页面的图片状态对应。
- 现有页面上的开发用文字，提案给了逐条的人话改法（[product-structure.md](product-structure.md) 的“只给他们看他们看得懂的”）。

## 4. 和现行合同冲突的（实施前要先定）

| # | 提案里 | 现行合同 / 数据 | 建议 |
|---|---|---|---|
| 1 | 今日备料按餐次写总份数（“午餐 · 160 份”） | D0：不显示人数 / 总份数，不补 1 | 只按每道菜写份数；没填写“份数没填” |
| 2 | 采购以“几箱、多少钱”为主体 | 已保存清单的人工判断（待核对 / 要买 / 有了 → 已买）是主体；需求变了要显式复核；估算只在资料齐全时给 | 每行先是人工判断，箱数和金额作为估算放在旁边；“排菜改了”提示改成“有 3 项要重新核对”，不自动改判断 |
| 3 | 按类别分组、“每一类在哪买”、“上次买了几箱” | 食材没有类别字段；供应商是每个食材的一段文字；`ShoppingList` 不存数量、价格和时间 | 测试周后按 schema → types → data → docs 加“类别”和包装叫法（箱 / 袋，三语）；在那之前按供应商分段（现有数据里供应商大致就是类别） |
| 4 | 菜品三态里“原视频的做法”可以直接排菜 | 只有师傅核定并明确采用某个版本后才能排；来源确认、厨房核定、采用是三个动作；菜单固定版本 | 三个标签放在知识库状态上：待核对 / 已核定（照原方或我们改过）/ 已用在菜单（vN）；选菜面板只列已采用的版本；库里有新版本时提示“本周用的是 v3，库里已有 v4” |
| 5 | “做完以后”里的“剩了很多 / 不够吃” | 实际供餐统计、反馈和报告不在本轮范围 | 先只保留“要不要改菜谱”的提示；份数和剩菜统计等扩大范围时再定 |
| 6 | 给帮厨看“怎么切”的原视频片段 | [ADR-0010](../../adr/0010-knowledge-source-access.md)：原片和参考图默认只给师傅 / 管理员；给帮厨要先确认使用权和发布路径 | 使用权确认前只显示文字和切法示意图（CutSpec） |

## 5. 仓库里有、提案没画的（第二轮要补）

- **谁是谁、怎么进来。** 没有账号；帮厨不是登录角色；师傅用带令牌的链接；采购保存判断也要令牌，但二维码上的 `#/purchase` 不带令牌。提案按角色给每人一个默认首页，需要先设计入口：三条链接 / 二维码各进哪一页、没有令牌时看到什么、令牌过期怎么说。
  - **已定（Terry，2026-10-14）：当前不需要令牌。** 测试周三张码都用不带令牌的链接。按现有代码，这意味着线上按未接写入服务的只读发布使用：采购页是只读预览，不能保存判断；只读预览也提供“复制给菜贩”（[#140](https://github.com/TERRYYYC/canteen-os/pull/140)）。如果线上接了写入服务，没有令牌的采购员会被挡在已保存清单之外，需要另定。
  - **已定（Terry，2026-10-14）：先藏起来。** 没有令牌时，底部导航不显示“菜单计划”，计划栏不显示“排菜 / 编辑”或“创建本周计划”，计划页顶栏的“导入”也不显示（[#142](https://github.com/TERRYYYC/canteen-os/pull/142)）。抽屉里的“师傅后台”“排每天的菜”保留，点进去由锁屏说明要用师傅链接。
- **吃饭的人看的菜单。** 测试周把“菜单”码贴在档口（[week-43 指南](../../field-test/week-43/README.md) §0），提案却把“菜单”拆进了备料和排菜。要么保留一个只读的“这周吃什么”，要么明确不再给他们看。
- **菜谱进来以后的复核 → 核定 → 采用。** 收件箱、来源审核、核定表单（核定人、备注、确认来源）、采用后排进菜单——提案只有标签，没有页面（对应 #124、#127）。
- **发布。** 一次发布全部改动，要几分钟（校验 → 翻译 → 构建 → 上线），会失败，可以回退，回退后不会自动上线。提案只有一行状态，没有进度、失败和回退。
- **微信 / CSV 粘贴排菜。** 现有功能，选菜面板之外要保留入口。
- **几种保护状态。** 冲突对照（保留我的 / 用新的）、保存结果不明先核实、离线、没有写入服务时只读——新页面稿都还没画。
- **食材的规格和价格谁来改。** 提案的食材页只读；上次价由谁、在哪更新还是 [采购模块](../../modules/procurement.md) 的开放问题。

## 6. 需要新做后端的（单独立项）

- **问师傅（AskChef）**：帮厨的身份、挂在“某天某餐 · 某道菜 · 某样食材”上的问答记录、推送到师傅手机、自由文字自动翻译并保留原话。
- **帮厨在 app 里提切法叫法（CutTerms）**：同上需要帮厨身份和写入。
- **采购历史**：每次实际买了多少、多少钱，才能显示“上次买了几箱”。

## 7. 切法叫法：一张跟着实践改的结构化表

切法、备料和烹饪用词（[`data/techniques.json`](../../../data/techniques.json)，32 个）不做一次性确认，而是一张跟着厨房实际使用改的表：

- 每个词一行：`id`、类别、三种语言的叫法和说明、状态、厨房里的叫法（按语言）、以前的叫法（按语言，搜索用）。
- 状态只有四个：未经实践 → 有疑问（有人问或做错）→ 试用中（刚改了叫法）→ 已确认（改后看懂了，没人再问）；已确认的词再有人问，回到“有疑问”。
- 每条记录：哪个词、哪天、什么事（问了 / 做错了 / 看懂了 / 平时这么叫 / 改了叫法 / 改了状态）、谁（角色，可加名字）、哪种语言、哪道菜、原话；改叫法写从什么改成什么和依据。
- 先观察 8 个乌语像逐字翻译的词：滚刀块、末、条、段、花刀、上浆、挂糊、拍粉。
- 改已有技法的叫法要出技法的新版本，不直接覆盖 `data/techniques.json`：worker 把文件里已有的条目当作固定的（内容不同会报 conflict），已批准的菜谱也记着每个技法的版本和 hash。

Terry 现在在 claude.ai 上有一张这样的工作表（私有）；测试周里帮厨看不懂的切法原话，可以直接记进去。

## 8. 测试周（10/19–25）顺带看什么

测试周代码冻结、只修 P0，schema 冻结。下面这些不需要改代码，只要在 [week-43 日志](../../field-test/week-43/log.md) 里按原话记，复盘周用来取舍本提案：

- **帮厨**：哪些切法叫法看不懂（原话）；有没有想问师傅却不方便问的时候；需不需要“对方语言”那一行；需不需要“做完了”的勾（已在第二轮清单）。
- **采购员**：实际按什么顺序买（类别 / 供应商 / 摊位）；“复制给菜贩”（[PR #140](https://github.com/TERRYYYC/canteen-os/pull/140)）能不能直接转发；还缺什么才敢下单（箱 / 袋叫法、规格、上次买了多少）。
- **师傅**：排菜时怎么避免重复；发布要等多久、哪里嫌麻烦；核定和采用菜谱的步骤是否顺手。
- **吃饭的人**：有没有人扫菜单码；看什么。
- **没有令牌的人**（帮厨、采购员、吃饭的人）：计划栏下拉里还写着“选择或创建”，会不会以为要自己建计划。[#142](https://github.com/TERRYYYC/canteen-os/pull/142) 只藏了入口，没改这句。
