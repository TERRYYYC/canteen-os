# CanteenOS · 全场景高保真设计交接

本稿依据用户提供的九屏参考图与食堂全流程需求，探索“知识入库 → 排菜单 → 备料采购 → 就餐体验 → 复盘”的产品形态。
它是本轮设计提案，不替代 [第一轮执行简报](../../execution-brief.md)、现有 v0.3、生产 schema、既有设计事实源及冻结计划。
视频导入界面、点菜、评分和运营报告属于愿景探索；原型中的操作与数字均为演示，不代表已上线、已提交订单或已真实解析视频。

> English summary: A ten-screen design exploration of the nine reference scenarios. Existing schema v2 and release boundaries remain authoritative; new customer and reporting flows are proposals.

## 1. 九类场景、十个画板与角色

沿用参考图的叶绿、暖白、菜品摄影、圆角卡片与清晰留白；工作页提升表格密度，移动端保留单手操作与明确的主要动作。

| 屏幕 | 主要使用者 | 关键信息与下一步 |
|---|---|---|
| 1 首页 | 顾客、厨师、采购 | 今日供餐与菜品亮点；按任务进入菜单、知识库或采购；显示当前语言 |
| 2 菜单 | 顾客 | 日/周/月、日期、餐次、分类；点菜品进入详情；点菜意向与生产计划份数分别展示 |
| 3 菜品详情 | 顾客、厨师 | 成品图、三语名、已知成分、过敏原、评价样本；进入做法或反馈 |
| 4 如何制作 | 厨师、帮厨 | 配方基准份数、备料量、切配图、分步操作、来源视频片段；份数调整联动用量 |
| 5 反馈 | 顾客、厨房团队 | 星级、口味标签、可选文字、反馈来源；提交后可确认内容与关联餐次 |
| 6 菜品知识库 | 厨师、采购 | 菜品/食材/调料入口、搜索与就绪提示；查看“能教/能排/能采”及缺项 |
| 7 视频与文件导入 | 厨师、内容 agent | 来源输入、处理进度、食材映射、低置信项、三语审核；导入为草稿 |
| 8 菜单计划 | 厨师、运营 | 日/周/月、餐次、每菜份数、备量系数；生成采购预览并查看差异 |
| 9 采购清单 | 采购 | 按供应商分组、包装数、待补全、逐行算式、复制与 CSV 导出 |
| 10 运营报告 | 运营 | 将参考图第九屏的报告独立成页；周/月切换、评分样本量和多方反馈 |

主要走查路径：知识库选菜 → 排一周菜单 → 生成采购预览 → 展开某食材来源 → 复制供应商清单。
扩展走查路径：视频/文件 → 待确认草稿 → 厨师校对 → 入库；菜单 → 菜品 → 点菜意向/评分 → 报告。
角色切换只用于原型展示任务视角，不等于新增登录或权限系统；正式权限仍遵循现有写入通道。

## 2. 知识库与三语

实体关系延续 [架构](../../architecture.md)：菜品引用食材，调料也是食材；切配和做法引用 `techniques.json`。
配料使用 `ingredientRef` 与 `Quantity {value, unit}`；中文“盐”、英文“Salt”、乌语“Сіль”映射同一个食材 ID，不能重复建三份库存。
知识库列表用“可备料 / 可排菜单 / 缺采购规格”等具体提示；系统可保存不完整草稿，采购计算只消费满足现有规则的数据。

三语包含两层：导航、按钮、错误提示等界面文案，以及菜品名、食材名、技法、步骤等实体内容。
实体沿用 `I18nString {zh, en, uk}`；内部单位与 ID 不随语言变化，显示时再本地化，乌克兰语代码固定为 `uk`。
语言选择展示“中文 / English / Українська”，保持当前页面、筛选和表单输入；长乌语文案允许换行，不裁掉数量或主要动作。
缺译文按 [现有规则](../../i18n.md)“请求语言 → zh → en → uk”去重回退；显示“当前显示中文，乌语待补”等标识，不让回退冒充已翻译。
机器译文显示“机器翻译 · 待核验”；依据 `translations.lock.json` 的 `machine/human/stale` 展示状态，缺记录不宣称已人工审核。
目前锁记录粒度是整个 I18nString，不能从共享 `human` 状态推断中、英、乌逐语种全部已校对；逐语种审核为后续设计议题。
人工译文不被机翻覆盖，原文变化后提示复核；厨师确认中文含义，乌语使用者核验动作、切配尺寸和数量，英文一并做溢出与术语检查。
未知过敏原、未核验营养和估算克重分别标清来源/状态；未提供数据不显示成“无过敏原”或精确营养结论。

## 3. 外部视频 skill → 标准文件 → 审核入库

复用 [video-recipe-ingest 契约](../../../skills/video-recipe-ingest/SKILL.md)与 [dish schema v2](../../../schemas/dish.schema.json)，本稿不创建另一套导入协议。
推荐界面顺序：选择视频链接/本地文件 → 解析进度 → 核对食材与用量 → 核对步骤与三语 → 保存草稿 → 审核入库。
外部云端、第三方或本地 agent 都可运行解析；产品端接受同一结构，不把某个模型品牌写进厨师的主要操作路径。
标准交付是 `data/dishes/<dish-id>.json`（`schemaVersion: "2"`、`status: "draft"`）与图片；图片归档位置按优先级更高的执行简报放在 `data/dishes/<dish-id>/images/`。
成品图、切配图、步骤图通过现有 ImageRef 引用，保留实际来源和许可元数据；单图 ≤ 200 KB、最长边 ≤ 1280，不凭“来自视频截帧”自动推定为自有图片。
保留 `provenance.videoUrl`、步骤 `clip {videoUrl,start,end}`、配料 `confidence`；缺数字、看不清、未匹配食材必须进入人工确认列表。
置信度 `<0.85` 沿用现有 skill 的审核优先级门槛；该数字是模型提示，不代表经过实测校准的正确率。
食材映射优先匹配已有 ID，技法只选现有受控词表；未匹配项先建议新建或换映射，不能把未知字符串直接写入引用字段。
视频原配方份数、推算份数与厨师确认份数在审核页区分；放大为食堂批量后，应由厨师核对并称重，不能把线性缩放当作已验证配方。
校验顺序：JSON/Schema → 跨文件引用 → 图片与时间段可追溯 → 就绪检查 → 厨师审核低置信项和译文 → PR 合入知识库。
缺关键字段可留作合法的不完整草稿；未通过引用/单位校验的候选不参与采购，修正后再复跑校验。
PR 承载人工审核记录；解析 agent 不自动把菜品设为 `active`。审核后按现有流程激活，入库与发布分别显示结果。
失败状态保留输入和可恢复草稿，注明失败发生在下载、转写、映射还是校验；演示进度须写“模拟流程”，不能显示真实解析成功。
批量 ZIP 仅作为未来运输封装草案：承载上述文件及清单、解包后逐菜校验；不恢复已移除的 dishpack 协议，也不改变 schema v2。
线上线下交换的是同一版本的文件与图片；展示数据版本和构建时间，离线查看缓存不等于离线修改已同步。

## 4. 菜单计划 → 采购：每个数字能展开

每个菜单条目表示“某日、某餐次、某道菜的计划供应份数”；同餐三道菜各 100 份不自动等于 300 位顾客。
点菜意向、预计就餐人数与 `plannedServings` 分别表达，正式计算以厨师确认的 `plannedServings/baseServings` 缩放配方。
日/周/月切换改变观察区间；生成清单前明确采购覆盖的日期和餐次，月计划不意味着鲜货一次买足整月。
以下表达与 [现有采购引擎](../../../packages/core/src/procurement/engine.ts)对齐，所有运算先归一到食材基准单位：

```text
net = Σ(配方净用量 × plannedServings / baseServings)
adjusted = (g/ml 食材 ? net / (yield ?? 1) : net) × (margin ?? 1.1)
need = max(0, adjusted − (trackStock ? 可扣减 onHand : 0))
need = 0 时不采购；need > 0 时先换算至 packUnit
packs = max(minPacks ?? 1, ceil(need / packSize))
采购量 = packs × packSize；预估金额 = packs × 上次每包装价格
```

`margin` 作用于全部食材，包括按个数采购的鸡蛋；`yield` 只作用于 g/ml。界面解释为“备量”和“处理后能用多少”。
库存完全覆盖需求时不因起订量额外采购；`trackStock=false` 不扣库存；`to-taste` 不编造采购量，备料单继续显示“适量”。
示例沿用仓库黄金数据：番茄炒蛋共 480 份，每份番茄净量 150 g，`yield=0.85`、`margin=1.1`、不扣库存。
番茄 `72 kg ÷ 0.85 × 1.1 = 93.1765 kg`；每件 5 kg，向上取整为 19 件 = 95 kg；每件 ¥28.50，预估 ¥541.50。
点开一行展示 trace：来源菜品/日期/餐次/份数 → 净需求 → yield → margin → 已扣库存 → 包装 → 取整 → 起订补足。
采购页显示生成时间和来源计划版本；当前 onHand 是文件快照，原型以数据版本提示其时点，不能称为实时可用库存或已预留库存。
缺采购规格或换算失败进入 `pending`，展示“未计入采购单”；无法得出完整数量时显示待定，其余有效行仍可预览。
采购模块旧文案中的“缺规格照常出单”不用于本稿；以实际引擎 pending 行为为准，且提醒采购员尚有缺项，不能把部分单称为完整单。
按 `purchase.supplier` 字符串分组，复制清单携带日期、品名、包数、总量与预估价；不同币种不混加，缺价不显示虚假的完整总额。
PO 沿用无状态的输出快照；下单、收货在现有流程中线下进行，原型不新增采购状态机。包装余量是采购差额，不能直接计为厨余浪费。

## 5. 反馈与周/月报告：后续扩展设计

此节定义界面及指标口径，尚不新增反馈实体、订单实体、数据库或采集端点；正式实施需进入后续范围决策。
顾客提供口味/份量/温度与星级；厨师提供可执行性、备餐偏差与耗时；采购提供规格、价格、缺货和替代品记录。
每条反馈关联日期、餐次、菜品、来源角色与原文语言；翻译作为辅助阅读保留原文，不把厨房/采购问题并入顾客星级。
顾客的点菜首先表达预订/偏好意向，原型明确是否可撤回和是否已确认；没有交易接入时不显示支付成功或实际销量。

| 指标 | 定义与必须显示的上下文 |
|---|---|
| 顾客平均分 | 有效顾客星级之和 ÷ 有效评分数；并列评分数 n、日期区间、餐次 |
| 反馈率 | 有效顾客反馈次数 ÷ 可核实的已供餐份数；分母缺失则不计算 |
| 点菜意向份数 | 区间内仍有效的已确认意向份数；不能冒充实际出餐或销售 |
| 供餐偏差 | 实际供应份数 − 计划供应份数；无真实记录时标“仅有计划” |
| 采购预估 | 已有价格行的包装金额合计，附未估价行数、币种和版本 |
| 实际成本/份 | 已核实的实际食材消耗成本 ÷ 同口径实际供应份数；不以采购支出直接替代 |
| 厨余比例 | 同一餐次可食用剩余重量 ÷ 已生产可食用总重量；不混入包装差额、骨皮和未测量项 |
| 运营问题 | 厨师/采购反馈按问题类型与处理结果统计，分别显示记录数 |

周报按食堂当地日期的完整自然周，月报按自然月；未结束的周期标“截至某日”，环比只比较相同天数和相同分母口径。
所有图表可看样本量、数据来源与更新时间；演示数据全程标“示例”。样本不足提示 n，不用少数好评推断全体顾客偏好。
反馈去重、匿名方式、截止时间与撤销规则为后续待定项；报告把未采集、零值与估算分开显示，不用零填充缺失数据。

## 6. 多人 / 多 agent 协作与验收

执行沿用 [AGENTS](../../../AGENTS.md)、[贡献指南](../../../CONTRIBUTING.md)和 [工作模式](../../operating-model.md)；本稿不另建任务队列或正式规范。
认领粒度建议：`schemas/` 与接口由契约负责人维护；`data/` 与翻译由知识库负责人维护；`packages/core/` 负责确定性采购；`packages/web/` 负责界面；`skills/` 负责解析适配；`packages/worker/` 负责既定写入通道。
同一 package 同时一位执行者；页面并行仅认领不同文件，共用路由、样式和字典明确唯一负责人。开工记录路径、输入版本、交付边界和依赖。
接口事实源保持为 schema、执行简报 §5、现有 ADR 和 core 类型；前端 mock 应与契约同构，不因设计增加生产字段。
对跨层实现按 schema → types → data → docs 推进；本轮仅设计探索，因此未触碰冻结实体，也不以设计稿授权新增接口。
交接记录 What / Why / Tradeoff / Open Questions / Next Action，附分支/提交、修改路径、验证命令、截图和未完成项。
作者可自测，独立 reviewer 负责复跑检查和指出问题；不能自批自己的实现。是否合并继续遵守仓库现有权责。
设计验收至少包括九屏可达、主路径连通、手机宽度和桌面截图对照，以及长乌语、缺译回退、空态、失败态、待补全状态。
数值验收使用黄金菜单复算包装数与金额；另检查库存覆盖、pcs 的 margin、缺规格 pending、单位失败及跨币种不混加。
中文厨师与乌语帮厨分别走查切配与做法，采购员核对清单是否可直接采购；截图通过不能替代这些实际可理解性验收。

## 7. 开源参照与本轮纠正（官方资料，2026-09-10 核查）

| 项目 | 官方核实与可借鉴点 |
|---|---|
| [Mealie](https://github.com/mealie-recipes/mealie) | AGPL-3.0；菜谱/菜单/购物清单。现有 [AI 导入](https://docs.mealie.io/documentation/getting-started/installation/ai-providers/)统一视频链接转写、文本、图片和链接，可选翻译；参考来源合并、字段审核与进度体验 |
| [Tandoor](https://github.com/TandoorRecipes/recipes) | 菜单到购物清单、份量缩放、食材/单位维护；[许可原文](https://github.com/TandoorRecipes/recipes/blob/develop/LICENSE.md)为 AGPLv3 加 Commons Clause 条件；参考编辑和组织概念 |
| [Grocy](https://grocy.info/) | [MIT](https://github.com/grocy/grocy)；官方明确支持菜谱/菜单与库存对照，将缺少项加入购物清单，另有最低库存与临期提示；参考库存参与需求计算 |
| [KitchenOwl](https://github.com/TomBursch/kitchenowl) | AGPL-3.0；多人实时购物清单、部分离线、菜谱、菜单计划和家庭支出；参考采购移动端协作形态 |
| [Cooklang / CookCLI](https://github.com/cooklang/cookcli) | MIT；纯文本菜谱、缩放、合并清单、JSON/Markdown 输出、库存配置及静态站生成；参考文件交换与自动化边界 |

上述是功能与许可证标签记录，代码引入仍按仓库白名单执行；不据此给出商业使用的法律结论。
本轮纠正：Grocy 已有库存参与清单生成，不能笼统称其“没有库存抵扣”；Mealie 已支持导入时翻译，不能笼统称其“完全不翻译内容”。
旧 Mealie `/open-ai/` 文档链接更新为表内 `/ai-providers/`；单次导入翻译也不等于已验证支持同实体三语并存。
在这五个项目的核查范围内，尚未确认一个完整覆盖本食堂全部流程的现成方案；不沿用“无人覆盖”“唯一开源”“开源空白”等绝对结论。
旧 `docs/research/` 保持只读；上述纠正记录于本提案，后续实现应逐项核对当前官方接口与实际数据模型。
