# CanteenOS 第一轮开发计划（给 Terry）

> 2026-09-07 起。设计阶段到此收尾。这份是给你看的：现在在哪、要做出什么、按什么节奏、你每周要做什么、什么时候喊停。给 agent 的执行细则在 `docs/execution-brief.md`，两份一起读，冲突时以本文为准。

---

## 1. 现在在哪

数据模型定案（5 个实体，ADR-0006），采购引擎能跑（23 个测试全绿，数字逐行手算过），乌克兰语备料单和微信采购单已经能从真实数据生成，视频解析的契约在一条真实视频上验过，前台三张单和后台七个屏的高保真你已经点头。

还没有的：网页本身、师傅能操作的后台、自动翻译、一个真实厨房的一周。

## 2. 要做出什么

一个网址，扫码打开，不上应用商店。四个页面：

```
帮厨   /prep      今天切什么、切成什么样、切多少（乌克兰语，有图）
采购员 /purchase  本周按供应商买什么，一键复制成微信消息
顾客   /menu      今天有什么、里面有什么（三语并列）
师傅   /admin     排菜单、加菜、按"发布"
```

改了菜单按"发布"，两分钟后三张单自动更新，中间没有人搬运。数据是仓库里的 JSON 文件；师傅不需要 GitHub 账号，拿到的是带钥匙的链接。

## 3. 节奏：四个版本，八周，收在一个真实的星期

| 版本 | 日期 | 做出什么 | 你要做什么 | 什么算完 |
|---|---|---|---|---|
| **v0.1 收尾工程** | 9/7–9/13 | 补齐数据字段（备菜"提前多久"、图片存放约定）、翻译脚本（DeepL + 术语表 + 不覆盖人工改动）、构建脚本雏形 | **确认真实厨房**：一位师傅、一位帮厨、一位采购员、一周真实菜单、菜贩清单（叫什么、怎么包装、上次多少钱）。和师傅谈一件事：每道菜要按 50 份称一次 | 脚本能把 data/ 变成三份文件；翻译脚本跑过一次 |
| **v0.2 三张单上屏** | 9/14–9/27 | 只读网页：/prep（A 版 + 点开看 B 版）、/purchase、/menu、左上角目录、离线可用；推送即上线 | 每周五看演示，用真实菜单的数据；把 /prep 给帮厨看 5 分钟，记他第一句话 | 三个页面在网址上能打开；断网能开上一次的；从改文件到页面更新没有人工步骤 |
| **v0.3 师傅后台** | 9/28–10/11 | /admin 工作台、排菜单（周视图 + 粘贴导入）、发布（进度 + 回退 + 二维码）、写入通道（云函数） | 你亲自用后台排一周菜单并发布；把采购链接发给采购员，让他自己复制一次微信文本 | 你连续一周没碰过 JSON 文件；采购员没让你替他生成过 |
| **v0.4 真实数据** | 10/12–10/18 | 用命令行把真实菜单里 ≥10 道菜导入（视频或手输），≥60 种食材含调料，技法词表补齐 | 陪师傅称 10 道菜（每道约 30 分钟，这是第一轮最贵的人力）；拍切配照片；帮厨把乌克兰语看一遍 | 10 道菜都到"能教"；帮厨看过一遍 uk |
| **真实厨房周** | 10/19–10/25 | 不开发。只修当天阻塞的错 | 每天记"不对"清单：帮厨看不懂什么、采购员改了什么、师傅嫌什么麻烦 | 见 §5 |
| **复盘 · v1.0** | 10/26–10/30 | 修测试周暴露的问题里最痛的三个；打 v1.0 标签；写一页复盘 | 决定第二轮做什么 | 第一轮结束 |

**两条铁律：** 日期可以往后滑，每个版本最多滑一周；滑超过一周就砍范围，不加时间。版本收尾前三天不加新东西，只修。

## 4. 你每周的固定动作

周一 30 分钟：看本周清单（不超过 5 项），砍掉第 6 项以后的。
周五 30 分钟：看演示，必须用真实数据；写三行——能用了什么、坏了什么、下周不做什么。
周末：不合并任何代码。

这三件事是"稳健"的全部含义。项目失控从来不是因为做得慢，是因为周一加了第 6 项、周五没看演示。

## 5. 什么时候喊停、什么时候往下走

三道门，过不了就停在门前，不往下走：

**门 A（v0.2 开工前）：真实厨房确认了吗？** 没有的话 v0.2 照做，但 v0.4 和测试周不排日期——没有厨房的软件只是演示。

**门 B（测试周前）：** ≥10 道菜能教、≥60 食材、帮厨看过 uk、采购员认过菜贩数据。缺一项就把测试周往后推，不带病测试。

**门 C（第一轮结束）：** 帮厨连续 5 天自己打开 /prep，没人发过截图；采购员连续一周自己复制微信文本；因缺料做不出的菜 = 0；生鲜多买 < 20%；新加一道菜到帮厨能看到 < 1 小时。全部满足才打 v1.0。

第二轮（11 月起）按测试周的"不对"清单排，不按路线图排。大概率是：视频导入和复核放进后台界面、帮厨勾"做完了"、翻译待审。

## 6. 五个风险和对策

**师傅不愿意称。** 这是最大的。对策：第一周只称 3 道最常做的，让他先看到帮厨用得上，再称剩下的。

**帮厨流动。** 这反而是产品价值所在——新帮厨第一天能看懂。把"新人上手时间"记下来。

**你是单点。** 第一轮接受。v0.3 后你退出日常链路（师傅自己排、自己发布）；第二轮把加菜也交出去。

**视频解析质量。** 没验证过真实 API。所以第一轮的新菜由你用命令行导入、师傅复核，不承诺自动化；API key 到位后再测。

**agent 写得快、验得少。** 上次鸡蛋那行的教训。对策写进了执行简报：黄金数字必须手算签名，每版一篇 ADR 上限，周五演示必须用真实数据。

## 7. 第一轮明确不做

任何写入界面之外的功能（帮厨勾选、采购员改包数）、登录、后端数据库、评分、报告、小程序、第二个厨房、视频导入的界面（命令行先顶着）。有人提这些，答案是"记到第二轮清单"。
